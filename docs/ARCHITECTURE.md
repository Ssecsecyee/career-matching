# 현재 시스템 아키텍처

상태: 배포된 구성 기준 · 기준일: 2026-11-02

## 대화 처리

```mermaid
flowchart TD
 U[React 사용자·관리자 화면] --> CF[CloudFront]
 S3[비공개 S3 웹 파일] --> CF
 CF --> API[API Gateway / Lambda]
 API --> Q[SQS 대화 작업 큐]
 Q --> W[EC2 Python 작업자]
 W --> B[Amazon Bedrock Sonnet]
 W --> DB[(MySQL 기준 데이터·대화·근거)]
 W --> ES[Elasticsearch 채용·교육 별도 색인]
 API --> D[(DynamoDB 임시 작업 상태)]
 W --> D
 DB --> O[search_outbox]
 O --> C[systemd 색인 소비 작업]
 C --> ES
```

Lambda는 요청 인증·검증과 작업 접수를 담당하고 SQS에 전달한다. EC2 작업자가 대화 실행, 검색 계획 검증, MySQL·Elasticsearch 조회와 Bedrock 호출을 수행한다. 브라우저는 작업 상태를 폴링한다. DynamoDB 임시 작업 상태와 MySQL 영구 대화 기록은 역할이 다르다.

## 현재 변경 방향

전체 공고 AI 백필은 보류하고 SQL 기준의 공고 선택 시 질문 정리·공유 캐시로 전환한다. 과거 표본 결과를 삭제하지 않는다. [선택 시 처리 계약](ON_DEMAND_CONDITION_REVIEW.md)을 따른다. 현재 구현/배포 상태는 해당 문서에서 구분한다.

## 데이터 경계

- MySQL: 공고·교육의 기준 데이터, 출처·버전·상태·원문, 세션·메시지·조건 답변·근거·모델 호출·응답 캐시·의도 판정 기록.
- Elasticsearch: MySQL에서 재생성하는 검색 사본. 채용·교육 색인을 분리하며 제목·본문·기술 등의 관련성 검색에 사용한다. 검색 후 MySQL에서 상세·버전·노출 가능 상태를 확인한다.
- Bedrock: 자유 입력의 문맥 의도·검색 계획과 상담 응답 생성. DB·ES를 직접 임의 실행하지 않으며 서버가 계약과 상태를 검증한다.
- S3: 웹 정적 파일과 배포 산출물 등에 사용한다. S3 사용만으로 DB 외부 백업이 확보됐다고 간주하지 않는다.

## 실행 환경과 장애 처리

한 t4g.medium EC2에 MySQL, Elasticsearch, 대화 작업자를 함께 둔다. DB·검색 포트는 외부 공개하지 않는다. Elasticsearch 가용성 장애 시 MySQL 검색으로 복귀하며, 검색 결과가 0건이라는 이유만으로 복귀하지 않는다. 단일 서버 장애는 세 구성요소에 함께 영향을 준다.

## 대화 실행

자유 입력은 ContextRouter에서 Bedrock 문맥 분류 → Pydantic 계약 검증 → 상태별 실행 검증을 거친다. 명시적 버튼·조건 답변·저장 답변 조회/수정은 직접 행동으로 처리할 수 있다. v3 단일화 구현을 AWS에 반영했으며 기존 DialogueFlow의 호환 의도 판정과 구형 혼합 모델 라우팅은 제거했다. 변경 계약·검증 범위는 [문맥 판단 단일화](UNIFIED_CONTEXT_ROUTING.md)를 따른다.

검색 기준 확인 → 공고 선택 → 필수조건 문답 → 중간 선택 → 우대조건 또는 상담 흐름을 지원한다. 사용자는 중단·재개·다른 결과·답변 조회/개별 수정이 가능하다. 미확인·미답변을 미충족으로 바꾸거나 합격을 판정하지 않는다. 상세 흐름은 기존 기능 문서를 참조하며 완전한 상태 전이표는 후속 정리 대상이다.

## 색인 동기화

검증된 적재에서 MySQL 데이터 변경과 search_outbox 이벤트를 같은 트랜잭션으로 기록한다. systemd 소비 작업이 DB의 이벤트를 읽고 최신 원본을 ES에 반영한다. 작업 종료 후 약 60초 간격으로 재실행하며 처리·장애 시간에 따라 지연된다. ID·버전으로 중복과 역순 반영을 방어한다. 수동 SQL 변경은 자동 이벤트를 보장하지 않는다. 상세: [검색 동기화](SEARCH_SYNC.md).

## 조건 질문 정리

신규 공고는 원문 MySQL/ES 검색 동기화까지만 수행한다. 전체 AI 백필은 보류하고, 사용자가 선택한 공고를 SQL에서 파싱한 뒤 질문 분류가 필요할 때만 모델을 호출하는 경로를 로컬 구현했다. 결과는 별도 질문 캐시로 공유하며 ES로 발행하지 않는다. 원문/조건 변경 시 재처리하고 기존 답변은 보존한다. AWS의 신규 캐시 테이블과 기능 활성화는 아직 반영하지 않았다. [선택 시 계약](ON_DEMAND_CONDITION_REVIEW.md)을 따른다.

## 후속 계획과 한계

고용24 API 수집 자동화는 미완료다. 목표는 예약 수집 → S3 원본 → 적재 전용 큐 → 검증·MySQL/Outbox 적재이며 현재 대화 큐와 구분한다. 추천 이유 A3, 정식 대화 평가, 외부 백업·복원 시험·경보는 각각 완료 증거를 확인해야 한다. 현재 구성과 향후 계획을 혼합하지 않는다.
