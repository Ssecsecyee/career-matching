> 최신 상태(2026-11-02): [AWS 배포 결과](STRUCTURED_SEARCH_DEPLOYMENT_20261102.md). 복합 검색·설명/확인·공고 표시를 AWS에 반영했고 실제 Sonnet 1회로 후보 10건 → 확인 후 5건 표시와 MySQL 기록을 검증했다. 경력 자동 필터와 상세 추천 근거는 후속 과제로 유지한다. 아래 미배포 표현은 당시 진행 기록이다.

기준일: 2026-11-02. 설계 MD 커밋 `bb5931ab3a2d9333cb2b2b8f0c97bfb688077cf1`은 main 푸시 확인 완료. 아래 구현은 로컬 코드이며 운영 배포 전이다. 실제 Bedrock·AWS·운영 DB 쓰기는 실행하지 않았다.

## 1. 구현 순서와 범위

| 단계 | 구현 |
|---|---|
| 검색 계약 | SearchPlan을 Pydantic 2 모델로 전환. 엄격한 타입·추가 필드 금지·개수/길이/연수 제한·불변 모델 |
| 이전 형식 호환 | 기존 keyword/region/skills는 v1 의미 그대로 보존. v2와 비어 있지 않은 구형 필드를 섞으면 거부. 기존 실험의 4개 위치 인자 생성도 호환 |
| 모델 출력 | 검색 JSON Schema를 Pydantic에서 생성해 프롬프트에 전달. 보유·필수 기술, 지역/직무 대안과 경력 선호 분리. 모델 SQL/DSL 실행 없음 |
| 검색 변환 | ES와 MySQL에서 지역 OR·직무 OR, 명시적 필수 기술 AND. 보유/선호 기술은 태그 일치 관련성 정렬 |
| 단독 기술 요청 | 직무/필수 기술이 없는 보유 기술 검색은 최소 하나의 보유 기술 태그 일치를 요구. React/Vue/Angular를 전부 필수로 묶지 않음 |
| 선호 유지 | 모델이 지역·직무 등 항목을 생략하면 기존 선호 유지, 명시적 빈 배열은 해제. ‘지역은 상관없어’는 지역 제한 해제 |
| 검색 설명 | 서버가 실제 적용 조건·순위 반영 조건·한계·검증된 건수로 생성. 설명용 추가 모델 호출 없음 |
| 확인 흐름 | 복합 요청/조건 변경은 search_review 단계. 공고 카드는 숨기고 [이 기준으로 공고 보기]·[조건 수정] 제공 |
| 확인 후 표시 | confirm_search와 현재 search_id 일치를 검사하고 MySQL에서 후보의 노출·버전 재확인. 정상 확인은 재검색/추가 Bedrock 호출 없이 저장 후보 표시 |
| 변경·0건 | 확인 전 공고가 변경/마감되면 카드 표시를 중단하고 같은 조건 재검색 안내. 0건은 실제 조건을 안내하며 자동으로 지역·필수 조건 완화하지 않음 |
| 간단한 즉시 요청 | ‘바로 보여줘’는 확인 생략 가능. 검색 조건 자체를 완화하지 않음 |

지역 별칭은 부산/부산광역시, 경남/경상남도 등을 공유 규칙으로 처리한다. 기술 별칭은 소규모 버전 사전이며 AngularJS를 Angular/Angular 2와 합치지 않는다. 모든 직군·표현의 포괄적 정규화를 완성한 것은 아니다.

## 2. 저장 위치와 호출 제한

- `chat_sessions.requirement_answers`의 `search_context`: 검색 ID, 사용자 요청 참조/원문, 원본 모델 계획(사용 가능한 경로), 실행 계획, 정책 버전, 조회 시각, 검색 요약, 후보 버전, 확인 시각. 기존 세션 만료·소유자 격리 적용.
- `chat_messages.structured_content._search_record`: 검색 설명/확인 응답과 같은 트랜잭션에서 기록. 다음 검색으로 현재 세션 계획이 바뀌어도 당시 검색 기록은 남는다. 이 내부 필드는 브라우저 응답에 추가하지 않는다.
- `response_cache`: 기존 요청 ID·소유자·상태 버전 기반 중복 방지 경로 재사용. 새 DDL이나 별도 검색 테이블을 생성하지 않았다.
- 버튼 확인은 모델 호출 한도 도달 후에도 추가 모델 없이 처리할 수 있도록 한다. 실제 모델 호출 제한은 유지한다. 자연어 확인은 기존 search 요청 진입이므로 한도 도달 후에는 버튼 경로를 사용해야 한다.
- 같은 검색의 후속 상담에는 실행 선호·검색 설명·이미 표시된 후보를 제한된 문맥으로 전달한다. 미확인 후보는 표시된 공고라고 전달하지 않는다.

새로운 공고별 일치 원문/필드 근거를 recommendation_evidence에 쓰는 전용 writer와 과거 검색 ID의 ‘왜 추천했어?’ 조회 기능은 아직 후속 과제다. 이번 검색 기록 저장을 상세 추천 근거 구현 완료라고 표현하지 않는다.

## 3. 중요한 한계

1. **경력 선호는 저장·설명하지만 실제 경력 자동 필터는 적용하지 않는다.** 현재 검증된 공통 경력 컬럼이 없어 신입~주니어를 임의의 숫자나 제목 단어로 판정하지 않는다. 화면에 미적용 사실과 공고별 확인 필요를 명시한다.
2. 전공·FFI 등 원문 경험을 보존하지만 보유 기술 순위는 현재 기술 태그 일치 기반이다. 의미 임베딩 검색이나 상세 경력/학력 자동 판정은 도입하지 않았다.
3. ES와 MySQL의 지역·필수/선호 논리는 같아도 본문 분석과 점수는 다를 수 있다. MySQL 복귀 시 이를 안내하며 정상 0건은 장애 복귀 사유가 아니다.
4. 이전 v1 호출은 원래 의미로 실행한다. 기존 요청을 근거 없이 자동 OR로 변경하지 않는다. 새 Bedrock 프롬프트는 v2를 지시하나 실제 모델 추출 품질은 별도 소량 검증이 필요하다.
5. 선호 해석과 AND/OR 의도 분류는 Pydantic이 보장하지 않는다. 엄격한 형식 검증·서버 정책·실제 모델 회귀 평가가 함께 필요하다.
6. 확인 전후 공고가 변경되면 현재는 자동 대체 목록 대신 재검색을 안내한다. 사용자가 확인한 목록을 조용히 다른 공고로 교체하지 않는다.

## 4. 의존성과 배포 준비

Pydantic 2.14.2를 requirements에 추가하고 로컬 AWS_project 환경에 설치했다. pydantic_core는 네이티브 라이브러리이므로 Windows 설치 폴더를 AWS에 복사하지 않는다.

- Lambda: `infra/python_dependencies.py`가 Python 3.11/Linux x86_64 휠을 별도로 구성해 API ZIP에 포함. 기존 Lambda 아키텍처를 유지한다.
- EC2 ARM: 신규 생성 bootstrap에 의존성을 포함. 코드 업데이트는 실행 중 worker를 멈추기 전에 ARM 환경에서 휠 설치와 SearchPlan import 검사를 수행한다. 실패하면 실행 중 코드를 교체하지 않는다.
- 실제 서비스 재시작·Lambda 코드 교체·웹 publish는 실행하지 않았다. 배포 시 dependency 설치를 포함한 새 build가 필요하며 과거 ZIP을 재사용하지 않는다.

## 5. 검증 기록

- 백엔드 237개 검사 중 228개 통과, 환경 의존 9개 제외. 운영 MySQL/실제 ES 통합 검증 완료를 뜻하지 않는다.
- 프론트 21개 검사 통과와 프로덕션 빌드 성공. 검색 확인 JSX를 실제 렌더링해 조건·건수·비활성/0건 버튼 표시 검사.
- 사용자 복합 문장의 모의 Bedrock 출력 → Pydantic → 검색 → 확인 흐름을 검증. 합성 자료에서 부산/경남 후보만 반환하고 서울 후보는 제외, 기술 전부 AND로 묶이지 않음을 확인.
- 실제 모델 호출은 0회. 모의 출력 성공은 Sonnet이 실제로 같은 계획을 항상 생성한다는 증거가 아니다.
- 구형 계약, 명시적 필수 AND, 지역 제한 유지/해제, 잘못된 JSON, 오래된 검색 ID, 원문 버전 변경, 추가 모델 없는 확인, 검색 기록의 트랜잭션 저장·브라우저 내부 기록 비노출 검사.
- Linux Lambda 휠 패키징 시험 통과. Windows .pyd/.dll 미포함과 Linux x86_64 core .so 포함 확인. AWS 런타임에서의 실행은 미검증.

## 6. 다음 단계

1. 주신 원문과 변형 문장으로 실제 Sonnet의 v2 해석을 소량 검증하고 지역 OR/직무 OR/필수·보유 구분을 대조한다. 실제 호출 비용·opt-in 범위를 확인한 뒤 실행한다.
2. 실제 MySQL·ES의 같은 후보 범위와 최신성/순위·0건, 세션 저장·재시도/격리를 소량 통합 검증한다.
3. 공고별 일치 필드·원문 근거와 사용자 발언을 연결하는 추천 근거 writer·조회 기능을 구현한다.
4. 배포 시 API/worker/웹 순서와 롤백을 검토해 함께 반영하고 브라우저에서 복합 요청 → 설명 → 확인 → 공고 표시를 검증한다.
