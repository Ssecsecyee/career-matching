## 2026-10-30 현재 적용 상태 (아래 과거 기록보다 우선)

기존 EC2를 t4g.medium(4GiB)으로 확장하고 ARM64 Elasticsearch 9.5.5·Nori를 설치했다. 동일 인스턴스와 EBS를 유지했으며 MySQL 채용 942건·교육 7건을 별도 색인에 반영했다. 엔진 green, 작업자 active, 검색 포트는 127.0.0.1:19200으로 제한한다. 16:09 측정 시 가용 메모리 약 2207MiB이며 부하 시험 결과는 아니다.

운영 챗봇의 검색 경로는 아직 MySQL이다. 최신 연결 코드·검색 선택 설정 적용, 운영 복귀 검증과 Outbox 자동 소비는 남아 있다. 실패 입력 선저장 보완도 로컬 검증 상태이며 운영 앱에는 배포하지 않았다. CloudFormation LaunchTemplate의 기존 t4g.small 설정은 실제 크기와 달라 후속 인프라 변경 전 안전한 정합화가 필요하다.

상세 실행·검증 기록: [AWS 검색 배포 결과](../infra/elasticsearch/DEPLOYMENT_20261030.md). 아래 날짜별 내용은 당시 이력으로 읽는다.


## 2026-10-29 초기 AWS 서버 배치 확정

초기는 기존 EC2를 확장해 MySQL·백엔드 작업자·Elasticsearch를 한 서버에서 함께 운영한다. 신규 검색 전용 EC2는 초기 배포에 추가하지 않는다. 이 결정은 과거의 서버 배치 미정 설명보다 우선한다. 인스턴스 유형·메모리·디스크·월 차액·점검 시간은 아직 미정이며 실제 크기 변경은 실행하지 않았다.

검색 포트는 외부에 공개하지 않고 같은 서버 내부로 연결한다. 검색 읽기/색인 쓰기 권한과 비밀 설정, 영속 볼륨·재시작 정책을 준비한다. 자원 제한으로 DB·작업자에 미치는 영향을 줄인다. 지속적인 메모리 압박/OOM, 검색으로 인한 DB 응답 악화, 색인 지연 또는 독립 배포·복구 필요가 확인되면 검색 전용 EC2 분리를 검토한다. 분리 수치 기준은 관측 후 정하며 정식 부하 검증은 고용24 파이프라인 단계로 이관한 합의를 유지한다.

## 2026-10-29 Elasticsearch 도입 합의와 구현 상태

이 절은 아래 과거 초안의 검색엔진 관련 설명보다 우선한다. **로컬 Nori·동의어 실행과 실제 스냅샷 783건 색인·검색 어댑터 검증을 완료했으며 운영 Elasticsearch는 미도입이다.** 직접 설치 방식으로 진행하며 OpenSearch·Elastic Cloud로 자동 대체하지 않는다. 로컬 Docker에서 분석기·색인·백엔드·동기화를 검증한 뒤 AWS에 배포한다. S3는 원본·백업 저장소이며 검색엔진 설치 위치가 아니다.

`infra`는 infrastructure의 약자로 실행·배포 환경을 관리한다. `infra/elasticsearch/`에 Nori 포함 Dockerfile, 로컬 Compose, 매핑·분석기·동의어 설정을 둘 계획이다. 검색엔진은 자체 디스크를 쓰는 서버 프로세스이며 S3에 설치하지 않는다.

AWS는 직접 설치로 진행한다. 기존 EC2 확장 또는 검색 전용 EC2 추가는 미정이다. 현재 t4g.small 2GB에 여유 확인 없이 함께 배치하지 않는다. CPU 아키텍처별 이미지·플러그인 호환성을 확인한다. 비용은 기존 대비 EC2 차액/추가 서버, EBS·백업·로그·네트워크를 계산한다. Bedrock 비용은 별도 호출·토큰 사용량으로 산정한다. 이번 합의는 유료 리소스 생성 실행이 아니다.

## 2026-10-28 최신 상태와 고용24 전환 계획

이 절의 실행 현황과 전환 방향을 아래의 과거 초안보다 우선한다. 현재 AWS 웹·대화 서버·EC2 MySQL 연결을 검증했으며 RDS와 Elasticsearch는 사용하지 않는다. 점핏 추가 표본 10건은 백업 후 운영 반영해 총 793건이며, 기존 783건의 버전·해시는 유지했다. 신규 10건의 모집 상태는 unknown이다. **고용24 승인 후 소량 표본 검증을 거쳐 AWS 정기 배치 자동화로 전환**한다. 상세 단계와 통과 기준은 [고용24 파이프라인 계획](../app/ingestion/GOYONG24_PIPELINE.md)을 따른다.

### 고용24 자동화 리소스 계획

승인 후 먼저 표본 요청과 매핑을 검증한다. AWS 자동화에는 수집 Lambda, 예약 트리거, 비공개 S3 수집 경로, 적재 전용 큐·실패 큐, EC2 적재 소비자와 단계별 최소 권한이 필요하다. 현 대화 큐와 기존 IAM 정책을 그대로 재사용할 수 있다고 가정하지 않는다. DB 외부 포트 개방·신규 RDS·NAT·검색엔진 생성은 이번 문서 수정으로 승인하거나 실행하지 않는다. 주기·1회 한도·키 보관·백업·로그·비용 알림을 검증한 뒤 배포한다.

## 이전

기존 로컬 데이터를 스냅샷으로 내보내 최초 적재하고 ID별 upsert로 검증한다. 건수·원본 ID·내용 해시를 대조한 뒤 변경분 수집으로 전환한다. 로컬 DB와 AWS DB 양쪽을 영구적인 쓰기 기준으로 두지 않는다.

## 네트워크와 권한

브라우저는 API만 호출한다. DB와 검색엔진 인증정보를 노출하지 않는다. Bedrock은 서버 실행 역할을 사용한다. 수집·적재·조회·색인 권한을 분리한다. DB와 Elasticsearch의 배치가 정해진 뒤 VPC, 보안 그룹, 외부 출처 접근 경로, 엔드포인트 또는 NAT 필요 여부를 결정한다. 기존 OpenAI 호출을 전제로 한 NAT 필수 설명은 적용하지 않는다.

## 비용

Bedrock 토큰, DB 고정·변동 비용, 검색엔진 고정비, 수집 실행, 네트워크 전송, S3, API, Lambda, 로그를 함께 산정한다. OpenSearch로 자동 대체하지 않는다. 예산 승인 전 유료 리소스를 생성하지 않는다.

운영 대화·판단 근거·모델 호출 기록·초기 응답 캐시는 기준 DB의 별도 테이블로 관리한다. Lambda 로컬 저장소는 영구 기록으로 사용하지 않는다. CloudWatch는 운영 로그, S3 장기 보관은 보존 정책 확정 후 사용한다. 별도 Redis 도입은 초기 필수가 아니다.


## 2026-10-28 실행용 배포 준비

infra/README.md에 CMD 실행 순서와 인수인계를 정리했다. template.json은 generate_template.py로 생성하고 deploy.py로 빌드·변경 세트 검토·적용·초기 적재·웹 게시·DB/토큰 집계를 수행한다. CloudFront OAC/비공개 S3, HTTP API/Python Lambda, 비공개 RDS MySQL, Secrets Manager, 두 AZ의 Bedrock/Secrets Manager 인터페이스 엔드포인트, S3 게이트웨이로 구성하며 NAT는 만들지 않는다. 호출 한도 12회·낮은 동시성·API 처리율 제한을 유지한다. 엔드포인트 ENI 4개와 RDS 등의 상시 요금이 있으며 크레딧 충분 여부와 월 비용은 아직 검증하지 않았다. 알림 금액·이메일을 지정하고 실제 생성 전에 변경 세트를 검토해야 한다. 배포/계정 권한/CloudFormation 스키마 검증/cfn-guard 보안 검사/실제 AWS 동작은 미확인이다. 로컬 검증은 AWS 호출을 수행하지 않았다.


## 현재 백엔드 실행 경로 보완

웹 호스팅 완료 후 저비용 백엔드 연결을 준비했다. 현재 우선안은 서울 t4g.small 단일 서버의 MySQL+Python 작업 코드와 Lambda/HTTP API/SQS/임시 DynamoDB 작업 상태이며 RDS/유료 VPC 엔드포인트는 사용하지 않는다. Elasticsearch는 아직 미포함이다. 기존 전체 배포 대신 infra/BACKEND.md의 backend.py를 따른다. 단일 서버/수동 운영의 한계가 있으며 월 6만 원은 목표이지 비용 상한 보장이 아니다. 실제 서버·DB·Bedrock 연결은 사용자 실행 후 검증해야 한다.
