# 성능 검증 지표와 평가 산출물 계획

작성일: 2026-10-30. 검색·추천 근거 개선과 함께 구현할 평가 계획이다. 지표 수집기·자동 평가·대시보드가 완성됐다는 뜻이 아니며 이번에는 부하·모델 호출·AWS 변경을 실행하지 않는다.

## 1. 평가 층과 비교 조건

성능은 검색 정확도, 근거와 대화 정책의 정확성, 지연·안정성·자원·비용을 구분한다. 결과 건수 증가, 일부 성공 예시, 메모리 여유만으로 전체 품질·동시 처리 성능을 선언하지 않는다.

- 검색 계층 평가: 고정된 구조화 검색 계획으로 DB/ES·분석기·동의어·AND/OR·순위 차이를 측정한다. 모델 해석을 우회하므로 대화 이해 개선의 증거로 쓰지 않는다.
- 대화 전체 평가: 같은 사용자 발화·이전 대화·선호·거절 상태를 넣어 의도→검색 계획→후처리→검색→근거 저장→후속 설명을 측정한다. 단일 기술과 복수 기술, 긴 문장, 짧은 후속 발화, 채용/교육 전환을 포함한다.
- 운영 평가: 프런트 요청부터 사용자가 유효한 결과를 받는 과정과 큐 대기·모델·검색·DB·저장을 따로 측정한다. 현재 한 서버 공동 운영 구조를 명시한다.

원본 데이터 해시·DB/색인 버전·별칭·기준 시각·시간대·모집 미확인 포함 여부·마감 정책·모델/프롬프트·정규화/동의어/가중치·호출 예산을 manifest에 고정한다. 비교 중 데이터가 바뀌면 분리 기록한다. 만료 경계를 지난 차이를 개선 효과로 취급하지 않는다.

비교 예: A 현재 정책, B 기술명 매핑만 보완, C 보유/필수 조건 조합 보완, D 직무 문맥과 순위 보완. 다른 조건은 고정하고 무엇을 바꿨는지 명시한다. 튜닝 세트와 미사용 평가 세트를 분리한다. 모델은 비결정성이 있으므로 실제 모델 평가 반복수·성공/실패·변동을 함께 기록한다.

## 2. 검색 품질

| 지표 | 정의와 분모 | 용도 |
|---|---|---|
| P@5 | 상위 5칸 중 관련 공고 수 / 5. 5건 미만이어도 빈 칸은 비관련 | 상단 정확도 |
| nDCG@5 | 0~3 관련성 라벨에 gain=2^등급-1, log2(순위+1) 할인 적용 후 해당 평가 집합의 IDCG로 정규화 | 순위 적합도 |
| MRR@5 | 첫 관련 결과 순위의 역수, 상위 5개에 없으면 0. 질의별 평균 | 첫 유효 결과 도달 |
| Target Hit@K | 사전에 지정한 유효 대상 중 적어도 하나가 상위 K에 있는 질의 비율. K=5/10 등을 고정 | 알려진 누락 회귀 |
| 후보 회수 여부 | 대상이 조회 후보 범위 안에 있는지. 상위 K 노출과 별도 보고 | 후보 생성/정렬 원인 분리 |
| 오답 0건 비율 | 유효 관련 공고가 존재한다고 판정된 질의 중 0건을 반환한 비율 | 부당한 검색 누락 |
| 올바른 0건 비율 | 유효 관련 공고가 없다고 판정된 질의 중 실제 0건 비율 | 무관 공고 남발 방지 |
| 필터 위반율 | 표시 결과 중 명시적 필수 조건·지역·마감 정책을 위반한 결과 / 표시 결과 | 검색 조건 정확성 |
| 표현 일관성 | 같은 의도의 별칭·띄어쓰기·설명 증감 변형에서 기대 의미와 유효 대상을 유지한 사례 / 판정 사례 | 자연어 견고성 |

관련성은 사람이 원문을 보고 0=무관, 1=약한 관련, 2=관련, 3=매우 적합으로 판정하며 2 이상을 관련으로 계산한다. 가능하면 비교군을 가린 독립 평가와 불일치 합의를 사용한다. 평가 의도·라벨 기준을 먼저 확정한다. 점수가 높아도 지원 자격·모집 상태가 자동으로 확인된 것은 아니다.

전체 공고에 대한 정답 집합이 없으면 전역 Recall을 계산하지 않는다. 결과 합집합 판정만 있으면 judged pool 기준임을 표시하고 미판정 문서를 정답 없음으로 바꾸지 않는다. IDCG=0 또는 라벨 미완료인 질의는 nDCG를 임의 0/1로 채우지 말고 계산 제외 사유·개수를 보고한다. 양성/음성 질의 지표를 나눠 전체 평균이 한쪽 오류를 숨기지 않게 한다.

55338125 공고는 저장 스냅샷상 유효한 조건에서의 회귀 대상 중 하나다. 항상 1위로 강제하지 않는다. 같은 9턴에서 문장을 줄일 때의 누락, Angular 계열·Vue 표기, 프론트엔드 선호 유지와 AND/OR 의도를 검증한다. 이 한 사례로 전체 검색 성능을 대표하지 않는다.

## 3. 의도·대화 기억·추천 근거 품질

| 문맥 유지 성공률 | 이전 희망 직무·선택 대상·교정 정보를 후속 턴에서 올바르게 유지/갱신한 시나리오 비율 | 다중 턴 검증 |
| 질문 거절 준수율 | 거절 후 명시적 재개 전까지 역량 질문·카드를 다시 강제하지 않은 시나리오 비율 | 화면 결과와 모델 최종/부분 응답 |

| 근거 참조 정확도 | 설명의 근거 참조가 같은 소유자·세션·추천 대상·원문 버전·사용자 발언을 가리키는 비율 | DB·스냅샷 대조 |
| 설명의 사실 뒷받침 비율 | 검증 가능한 설명 주장 중 저장된 발언/공고/실제 검색 특징으로 지지되는 주장 비율 | 주장 단위 사람 평가 |
| 무근거 주장률 | 지지 자료 없이 단정한 주장 / 검증 가능한 주장. 저장돼 있다는 이유만으로 올바른 설명으로 판정하지 않음 | 주장 단위 평가 |
| 근거 조회 응답 성공률 | 유효 근거가 존재하는 이유 질문에서 해당 기록을 조회해 맞는 설명을 한 비율 | 후속 질문과 조회 이력 |

| 격리/만료 위반 수 | 다른 소유자·세션 또는 만료 근거를 노출·사용한 건수 | 음성/권한 테스트 |

빈 근거 기록을 만든 것만으로 커버리지 통과로 세지 않는다. 근거 저장 실패·오래된 캐시·재시도·공고 버전 변경·이미 만료된 기록·표시되지 않은 후보를 별도 시험한다. 원래 근거가 없던 과거 추천은 '유효 근거 존재' 분모에 섞지 않고 별도 한계 안내 정확도를 평가한다.

LLM을 보조 평가자로 쓸 수 있지만 사람이 확인한 독립 라벨과 분리한다. 답변한 모델이 자기 답변을 높게 평가한 값을 사실 정확도의 최종 판정으로 사용하지 않는다. 사용자 내부 추론을 수집하는 대신 확인 가능한 원문·판정·참조를 사용한다.

## 4. 속도·안정성·동기화

| 지표 | 측정 구간/정의 |
|---|---|
| 검색 p50/p95 | ES 요청 및 MySQL 재확인을 분리하고 합산도 보고. 모델 시간과 분리 |
| 사용자 응답 p50/p95 | 프런트 요청 시작→최종 유효 응답 표시. 비동기 작업의 큐 대기·폴링 시간 포함 |
| 첫 유효 콘텐츠 시간 | 요청 시작→실제 생성된 첫 답변/유효 결과가 표시된 시각. API 202·로딩 문구·프런트 타이핑 효과를 모델 첫 토큰으로 세지 않음 |
| 구간 지연 | 큐 대기, 모델, DB, 근거 저장, 최종 전달을 request_id로 연결 |
| 성공/실패율 | 논리 요청 단위 성공·502/503/타임아웃·모델 출력 오류·DB/근거 저장 실패. 재시도 시도 수는 별도 |
| 처리량 | 명시된 동시성·측정 시간에서 완료한 논리 요청/초. 제출 수를 완료 처리량으로 사용하지 않음 |
| 재시도·복귀 | 재시도 성공률·중복 메시지/근거 수·ES 장애 MySQL 복귀 성공·정상 0건의 불필요 복귀 수 |
| 동기화 지연 p50/p95 | DB 변경 커밋→해당 버전이 ES 검색에 실제 노출/제외되는 시간. Outbox processed_at만으로 대체하지 않음 |
| Outbox 상태 | 대기 수·가장 오래된 대기 시간·반복 실패 수·회복 후 적체 해소 시간 |

지연 분포에는 표본 수·동시성·워밍업·캐시 적중 여부·모델·실패/중단 건수를 함께 기록한다. 성공한 요청만의 p95와 전체 오류율을 함께 보고하고 실패 요청을 조용히 버리지 않는다. 5회 측정의 p95를 운영 처리 한도로 주장하지 않는다. p95는 충분한 표본(예: 독립 요청 100개 이상)을 확보하는 방향으로 설계하되 실제 모델 호출 수·예산 승인은 부하 실행 전에 별도로 정한다.

초기에는 오프라인/모의 모델로 부하 도구를 검증하고 실제 검색·DB와 모델 포함 전체 요청을 분리한다. 동시성 단계·실행 시간·데이터 크기와 중단 조건을 정한 뒤 부하를 올린다. 큰 부하 시험은 기존 합의대로 고용24 데이터 파이프라인 단계에서 수행하며 이번 문서 추가가 실행 승인은 아니다.

## 5. 자원·토큰·비용

- EC2 가용 메모리, MySQL·ES RSS, JVM 힙/GC, CPU·크레딧, 디스크 여유·I/O·색인 크기·OOM/재시작 수를 시간축과 함께 수집한다. 컨테이너 제한 대비 사용률과 서버 전체 대비 사용률을 구분한다.
- 논리 요청당 모델 호출 수, 시도 수, 입력/출력·프롬프트 캐시 읽기/쓰기 토큰을 나눈다. 애플리케이션 응답 캐시와 모델 프롬프트 캐시는 같은 지표가 아니다.
- 추천 근거 payload 크기·DB 증가량·조회량·로그 증가량을 수집한다. 성공 세션당 비용과 실패/재시도 비용을 따로 본다.
- 비용 추정은 측정 당시 검증한 모델·리전·단가·환율·세금 적용 여부와 산식을 기록한다. 토큰 카운터는 계정 청구서가 아니며 EC2·EBS·IPv4·S3 등 고정/사용 비용과 별도로 보고한다. 실제 청구 확인 자료는 지연·다른 워크로드 혼입을 구분한다.

## 6. 초기 통과 기준과 미정 목표

- 고정 회귀 세트의 필수 조건 보존·마감/소유권/만료 차단·질문 거절 준수·unknown 비과대판정은 누락/위반 0건을 필수로 한다. 유효 추천 근거 연결은 고정 검증 대상에서 100%를 목표로 한다. 작은 시험 세트의 100%가 운영 전체 100%를 보장하지 않는다.
- 검색/설명 품질은 동일 평가 세트의 현재 기준값을 먼저 산출하고 비교한다. 대상 공고 회수와 직무 관련성 개선을 함께 검증하고 다른 질의 버킷의 회귀도 보고한다. 최종 수치 목표는 baseline·라벨 확보 후 확정한다.
- 응답 p95·처리량·오류율·동기화 지연·비용의 서비스 목표값은 현재 미정이다. 1분 타이머가 p95 동기화 60초를 보장한다거나 메모리 여유가 사용자 수 상한을 보장한다고 적지 않는다.

## 7. 평가 데이터와 산출물

구현할 산출물은 cases.jsonl(문맥·gold 의도/계획·유효 대상·시각), judgments.csv(관련성/근거 주장 판정), manifest.json(환경·버전·데이터), measurements.jsonl(구간/토큰/오류/재시도), metrics.json(값·분모·표본 수·제외 사유), REPORT.md(전후 표·변동·회귀·제한)다. 이름은 구현 계약을 확정할 때 고정한다.

민감정보 없는 합성 회귀 데이터와 평가기는 소스에 둘 수 있다. 실제 사용자 원문·평가 로그·상세 결과·DB 덤프는 Git 제외 workspace 평가 경로에 보관하며 같은 보관·접근 정책을 적용한다. 결과를 위해 임의 사용자 기록을 외부 평가 서비스에 보내지 않는다.

1. 지표 정의·gold 작성·환경/기준 시각 고정.
2. 기존 검색 지표 계산기를 재사용 가능한지 확인하고 대화·근거·지연 수집기를 추가.
3. 현재 구현의 baseline 수집 및 분모·제외 사유 검사.
4. 검색·근거 개선 후 같은 세트로 전후 비교, 미사용 평가 세트로 재검증.
5. AWS 소량 검증과 사용자 시나리오 확인 후 배포 기록에 결과 연결.
6. 데이터 확장 단계에서 별도 승인된 실제 부하·비용 검증과 운영 알림 연결.

기존 783건·18개 구조화 질의 비교 실험은 탐색용 기준 자료다. 현재 942건 DB/825건 검색 사본과 같은 데이터라고 가정하거나 그 실험만으로 대화 기억·추천 근거·운영 부하가 검증됐다고 표시하지 않는다. 새 baseline은 수집 당시 실제 스냅샷을 기록한다.
