# 문맥·의도 분류 평가 기준

기준일: 2026-11-02. 이 문서는 평가 설계와 제안 합격선이다. 실제 모델의 측정값이나 달성 결과를 뜻하지 않는다.

## 평가 대상을 분리한다

1. 분류 품질: 사용자 입력과 고정 문맥을 보고 target/action/변경 필드를 올바르게 판단했는가.
2. 서버 실행: 의도가 맞을 때 올바른 검색·다음 목록·상담을 실행하고, 불가능한 행동은 차단하는가.
3. 상담 답변: 자기평가·미확인·미답변·공고 버전을 구분하고 근거 없는 이력·채용 판정을 만들지 않는가.
4. 운영성: 성공·실패를 추적할 수 있고 호출 수·지연·토큰 사용이 허용 범위인가.

모의 모델 테스트는 2번의 검증이며 1번 정확도 증거로 사용하지 않는다. 실제 검색 결과 건수는 데이터 시점에 따라 달라지므로 의도 정답으로 사용하지 않는다.

## 고정 데이터와 정답

현재 experiments/context_intent/cases.json 21건은 개발·회귀용 합성 사례다. 전체 문맥을 보완하기 전에는 실제 모델 평가 입력으로 완성됐다고 보지 않는다. 정식 평가용 120건은 별도로 고정하고 프롬프트 수정에 재사용하지 않는다.

| 그룹 | 목표 건수 |
| --- | ---: |
| 새 채용 검색 | 10 |
| 채용 조건 수정·해제 | 10 |
| 채용 다음 목록 | 10 |
| 교육 검색·조건 변경 | 10 |
| 교육 다음 목록 | 10 |
| 교육 비교·설명 | 10 |
| 선택 공고 상담·준비 | 10 |
| 저장 답변 요약·근거 | 10 |
| 문답 중단·재개·우대 진행 | 10 |
| 대상 모호·참조 없음 | 10 |
| 검색 확인·확인 전 다음 요청 | 10 |
| 일반 대화·화제 전환 | 10 |

같은 “딴거”를 채용/교육/참조 없음 문맥에 각각 넣고, 긴 복합 문장·오타·짧은 생략·주제 전환도 포함한다. 각 사례는 message, 최소 상태 스냅샷, 허용 target/action 집합, 변경 허용 필드와 반드시 유지할 필드, 실행/미실행 기대값을 기록한다. 두 사람이 독립 라벨링하고 불일치는 합의하거나 모호 사례로 남긴다. 하나의 답이 없는 문장을 임의로 오답 처리하지 않는다.

문맥에는 이전 목록·선택 공고·검색 조건·문답 진행 상태를 실제 입력과 동일하게 채운다. 평가자는 실제 개인정보 대신 합성 대화·합성 ID를 사용한다. 데이터/모델 ID/프롬프트·스키마·검색 정책/실행 시각을 함께 고정한다.

## 지표와 제안 합격선

| 지표 | 계산·판정 | 제안 기준 |
| --- | --- | --- |
| 대상+행동 공동 정확도 | 둘 다 정답인 건수 / 전체 | 95% 이상 |
| 행동 Macro F1 | 행동별 precision/recall을 계산 후 평균 | 0.90 이상 |
| 구조 유효율 | JSON·Pydantic 검증 통과 / 전체 | 99% 이상 |
| 조건 보존율 | 수정 요청에서 미지정 필드가 유지된 건수 / 수정 사례 | 100% |
| 다음 목록 중복률 | 이전 노출과 겹친 ID / 다음 표시 ID | 0% |
| 위험 오실행 | 모호·선택 없음·버전 변경·중단 요청에서 잘못 실행 | 0건 |
| 기록 완전성 | 요청·분류·실행·실패 추적 가능한 건수 / 대상 요청 | 100% |
| 버튼 분류 호출 | 명시적 버튼에서 intent_classification 호출 수 | 0회 |
| 분류 지연 p95 | 모델 분류 시작→검증 완료 | 초기 목표 8초 이하 |
| 검색 전체 지연 p95 | 입력 수신→최종 검색 응답 | 초기 목표 15초 이하 |
| 상담 전체 지연 p95 | 분류·자연어 생성·저장 포함 | 초기 목표 40초 이하 |

지연 목표는 실제 사용 환경·부하를 기록한 뒤 조정하는 운영 목표다. 소수 smoke 호출로 p95나 전체 정확도를 발표하지 않는다. 위험 오실행이 있으면 전체 정확도가 높아도 전환을 보류한다. 120건이면 1건이 약 0.83%p이므로 건수·분모와 신뢰구간을 함께 제시한다.

조건 병합과 권한 검증은 모델 정답과 별개로 서버 결정적 검사에서 100%를 요구한다. 모델이 맞힌 검색이라는 이유로 조건을 조용히 완화하거나 확인 없이 필수 조건을 삭제하지 않는다.

## 실제 호출·비용 비교

버튼과 자유 입력을 구분해 분류/답변 호출 수, 입력·출력·캐시 토큰, 재시도 횟수, 실패 호출을 기록한다. 가격을 계산할 때는 당시 공식 단가·리전·모델/추론 프로필·가격 버전을 고정하고 AWS 청구액과 앱 추정값을 구분한다. 실패 호출과 분류 호출도 비용 집계에 포함한다. 자유 상담은 분류+답변 2회일 수 있으므로 1회 답변당 총합으로 비교한다.

Sonnet 기준 결과를 먼저 측정하고 동일 테스트셋으로 소형 모델 후보를 비교한다. 단일 평균 비용보다 의도 정확도·위험 오실행·p95 지연을 함께 판단한다. 자동 유료 재시도는 평가 도구에 넣지 않는다.

## 오류를 분류하는 방법

- context_error: 잘못되거나 누락된 문맥을 전달함.
- classification_error: 충분한 문맥에서 모델의 target/action/patch가 틀림.
- format_error: JSON/계약 검증 실패.
- execution_error: 분류는 맞지만 서버가 다른 행동/조건으로 실행함.
- retrieval_error: 실행 조건은 맞지만 검색 결과·최신성 검증에 문제.
- response_error: 상담이 원문·자기평가를 왜곡하거나 사실을 만듦.
- audit_error: 로그 유실·pending 미정리·호출 연결 누락.

intent_decision_id와 request_id로 intent_decisions·model_invocations·chat_messages를 대조한다. 동일 요청 재전송은 새 모델 호출/새 판단을 만들지 않는지 별도 확인한다. raw_output과 문맥은 제한된 운영 디버깅 자료이며 보고서·공개 Git에는 넣지 않는다.

## 실행·보고 순서

1. 계약/서버 분기 모의 검사와 격리 MySQL 테스트.
2. 소량 실제 모델 smoke로 배포·기록 연결 확인. 이 결과를 전체 정확도로 표현하지 않는다.
3. 독립 고정 120건 평가 및 실패 사례 수동 검토.
4. 별도 다중 턴 검증: 채용→다음→조건 변경→선택→문답→상담→교육→다음→채용 전환.
5. 승인된 기준으로 Sonnet/소형 모델 비교 후 운영 모델 선택.

보고 표에는 데이터셋 버전·사례 수·전체 성공/실패·대상/행동 혼동행렬·오류 유형·토큰·지연·미측정 항목을 포함한다. 현재 21건 개발 사례와 120건 정식 평가를 섞지 않는다.
