## 실제 서비스 검증

별도 합성 QA 세션으로 자연어 검색 → 검색 기준 확인 버튼 → 자연어 다음 요청 → 다음 공고 버튼을 실행했다.

| 단계 | 확인 결과 |
| --- | --- |
| Python·Docker 경험으로 백엔드 공고 요청 | Sonnet jobs/search 분류·서버 검색 확인 단계 정상 |
| 검색 기준 확인 버튼 | 모델 분류 없이 confirm_search 실행 |
| “그거 말고 또 볼 만한 곳은?” | Sonnet next_results 분류, ES의 다음 목록 정상 |
| 다음 공고 버튼 | 추가 모델 호출 없이 다음 목록 정상 |

첫 후보 85건, 자연어 다음 목록의 남은 후보 80건. 세 목록에서 각 5개, 총 15개 ID 중복 0건. 수치는 해당 QA 시점·추출된 조건의 결과이며 고정 정답 건수가 아니다. 보유 기술 Python/Docker가 순위 조건으로 유지되고 요구하지 않은 required_skills가 생기지 않았음을 검증된 판단 기록으로 확인했다.

DB에서 판단 기록 4개(모델 2·직접 행동 2)의 validation_status=validated와 execution_status=succeeded, 정책 v2, 실행 순서 search/confirm_search/next_results/next_results를 대조했다. 모델 호출은 intent_classification 성공 2회, 입력 4,711·출력 264토큰. 버튼 두 건은 분류 모델을 호출하지 않았다. 원본 채용 975건·교육 7건 유지.

## 최초 오류와 수정 근거

v1의 첫 실제 분류는 jobs/search였으나 중첩 스키마가 구형 keyword까지 노출해 v2 계획에 keyword가 섞였다. 계약 검증 실패를 DB에 보존하고 즉시 기존 경로로 복귀한 뒤, v2 전용 IntentJobPlan으로 모델 경계를 분리했다. 구형 필드를 임의로 삭제해 통과시키지는 않는다. 원문 반출 없이 필드 자료형·구형 필드의 비어 있지 않음·오류 위치만 진단했다.

최초 실패 호출 1회도 기록에 포함된다(입력 2,301·출력 179토큰). 이번 배포 QA의 합계는 성공 2회+실패 1회, 입력 7,012·출력 443토큰이다. 앱 기록이며 AWS 청구액이 아니다.

## 로컬 검증과 한계

로컬 Docker 격리 DB를 연결한 백엔드 전체 316개 중 314개 통과·다른 환경 의존 2개 제외. 실제 MySQL 통합 검사 9건을 포함해 새 테이블 생성·성공/실패 감사 기록·재전송·소유자 격리·모델 한도 이후 비모델 동작을 검증했다. 프론트 27개 통과·빌드 성공.

실제 모델 검증은 검색과 다음 목록의 소량 smoke다. 교육·상담 전 행동의 모델 정확도를 검증한 것이 아니고, 21건 개발 사례 및 별도 120건 평가를 완료했다고 해석하지 않는다. p95·정식 정확도·소형 모델 비교는 미측정이다. 기준은 [평가 기준](CONTEXT_INTENT_EVALUATION.md)에 분리했다.

## 추적·복구

응답의 request_id/intent_decision_id와 intent_debug_queries.sql로 당시 문맥·분류·실행·호출을 연결해 확인한다. 원본 로그·세션 ID·인증 정보는 Git에 저장하지 않았다. 설정 백업은 서버 보호 경로에 보존했다. 문제 시 CONTEXT_ROUTING_ENABLED=false로 되돌리면 기존 경로로 복귀하며 추가 테이블과 실패 기록은 보존한다.
