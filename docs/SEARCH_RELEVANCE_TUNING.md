# 검색 가중치 조정과 평가 방법

작성일: 2026-10-29. 이 문서는 운영·평가 계획이다. 사용자 기록을 학습해 가중치를 자동 변경하는 기능은 아직 없다.

## 현재 구성과 범위

- 채용: career-jobs-local-read 별칭. 제목·업무·자격요건·우대사항·기술 본문 검색과 별도 기술 조건, 지역·모집·마감 필터. 현재 기술 조건은 태그 분석 필드에 한정돼 본문만의 기술 일치까지 확대하는 후속 수정이 남아 있다.
- 교육: career-training-local-read 별칭. 제목·기관·커리큘럼·지원조건·우대조건·혜택·선발절차·유의사항과 주제·기술 배열을 검색한다. 채용 색인과 혼합하지 않는다.
- 교육 결과는 MySQL의 source+ID·버전·최신 사실을 확인해 카드로 만든다. 모집 상태 unknown/과거 회차는 학습 참고용이며 점수가 높아도 현재 신청 가능으로 바꾸지 않는다.
- 가중치는 초기 가설이며 검증된 최적값이 아니다. 교육 query는 태그/주제 4, 제목 4, 커리큘럼 3, 나머지 본문 1이다. 정확한 최신 구현은 app/backend/src/repositories/elasticsearch_training.py의 build_training_query를 따른다. 채용은 elasticsearch_jobs.py의 build_query를 따른다.
- 로컬 교육 7건 적재·색인·실제 DB 확인 후 React/리액트 각 3개 카드, Python 1개 카드, UI/UX 0개 카드 확인. 전부 신청 후보 0개다. 새 교육 수집을 했다는 의미가 아니다. 작은 표본으로 운영 정확도를 주장하지 않는다.

## 검색 로그와 Bedrock 답변의 용도

사용자 검색 기록과 답변은 개선 사례를 찾는 자료다. 모든 조정이 이 자료만으로 이뤄지는 것은 아니다. 분야별 전문가/사용자가 매긴 관련성 라벨과 오프라인 평가도 필요하다. 모델이 상단 결과를 반복 인용했다는 사실은 그 결과가 정답이라는 증거가 아니다.

현재 chat_messages, chat_sessions, model_invocations, recommendation_evidence는 대화·호출·판정 근거를 추적한다. 검색 점수·정확한 순위·클릭/노출과 가중치 버전까지 완전히 기록하는 검색 분석 로그는 아직 구현하지 않았다. 기존 테이블에 모두 있다고 가정하지 않는다.

추가할 검색 이벤트 계약:

| 항목 | 기록 이유 |
|---|---|
| request_id·익명 session_id·시각·검색 의도(job/training) | 대화/모델 호출과 연결 |
| 사용자 원문 또는 비식별 요약·정규화된 SearchPlan/교육 topics | 의도 분류와 검색 변환 오류 구분 |
| index/alias가 가리킨 물리 색인·분석기·동의어·쿼리/가중치 버전 | 당시 결과 재현 |
| 필터·최종 DSL 또는 검증된 구조화 조건 | 원인을 비교 |
| source+ID·source_version·노출 순위·검색 score·DB 확인 제외 이유 | 색인 지연과 관련성 구분 |
| 사용자 클릭/선택·다시 검색·명시적 적합/부적합 피드백 | 행동 증거 |
| Bedrock 호출 ID·모델/프롬프트 버전·답변이 인용한 근거 ID | 모델의 근거 사용 평가 |

접속 토큰·API 키·비밀번호는 수집하지 않는다. 자유 대화의 개인정보는 제거/최소화하고 보존 기간·열람 권한·삭제 정책을 정한다. 로그 저장을 위한 무제한 모델 입력/출력 복제는 하지 않는다.

## 오류를 먼저 분류

1. 데이터 없음/오래됨: 수집·갱신으로 해결. 가중치로 없는 과정을 만들지 않는다.
2. 교육→채용 오분류 또는 대화 기억 누락: 대화 상태·의도 분기 수정.
3. 한국어·C++·별칭 토큰 문제: analyze API로 색인/검색 분석 결과 확인 후 분석기·사전 수정.
4. 필터 과도함: 기술 AND/OR와 지역·날짜 의미를 검토. 관련성이 높다는 이유로 필수 필터를 우회하지 않는다.
5. 관련 문서가 후보에 있으나 아래에 있음: 가중치/순위 튜닝 대상.
6. 관련 문서가 후보에 없음: 검색 대상 필드/쿼리 범위/분석기를 먼저 수정. 점수만 올려도 후보에 없는 문서는 나타나지 않는다.
7. 결과는 적합한데 Bedrock이 잘못 설명: 프롬프트·입력 근거·생성 검증 개선. 검색 가중치 문제로 돌리지 않는다.

## 초기 튜닝 절차

1. 실제 실패/성공 검색 사례를 모으되 희귀 분야·0건·한국어·기술기호·교육 후속 질문을 포함한다.
2. 같은 질문·문서 스냅샷·기준 시각·필터로 기존/후보 가중치 결과를 각각 저장한다. 날짜 경과로 모집 필터가 달라진 결과를 가중치 효과로 비교하지 않는다.
3. 결과 합집합을 검색 방식·점수를 가리고 0=무관/1=약한 관련/2=관련/3=매우 적합으로 판정한다. 두 평가자가 다르면 근거를 확인해 합의한다. Bedrock의 잠정 평가는 보조 의견이며 확정 라벨이 아니다.
4. 튜닝용 질문과 미사용 검증 질문을 세션/질의군 기준으로 분리해 누수를 막는다. 소수 클릭에 맞춰 모든 사용자의 가중치를 바꾸지 않는다.
5. 한번에 한 가설만 비교한다. 예: ‘커리큘럼 비중을 3→5로 올리면 제목에 기술이 없는 실습 과정을 더 적절히 노출하는가?’ 숫자는 예시이며 아직 적용하지 않았다.
6. P@5/nDCG@5/MRR과 0건·필터 위반·DB 버전 불일치·응답 지연을 함께 확인한다. 전역 정답셋 없이 전체 Recall을 주장하지 않는다. 결과가 없는 질의는 적합 문서 부재와 검색 실패를 구분한다.
7. 개선을 확인한 설정에 버전을 붙여 로컬 회귀 테스트 후 배포하고 이전 설정으로 복귀 가능하게 유지한다. 온라인 A/B는 사용자 수와 기록 품질이 충분해진 뒤 수행한다.

## 어떤 값을 조절하나

`title^4`, `curriculum^3` 같은 필드 boost는 관련성 점수에 대한 상대적 기여다. 4가 특정 점수나 확률, 4배 적합성을 보장하지 않는다. 기술 태그의 boost와 본문 boost도 함께 작용한다. BM25의 k1/b는 초기에는 기본값으로 두고 필드·질의 설계와 분석기부터 검증한다.

지원 마감/모집 상태/지역 제한은 사용자 의도에 따른 필터이며 boost로 대신하지 않는다. 단순 최신 등록일이 학습 적합성을 보장하지 않으므로 최신성 boost는 실제 모집·일정 확인 뒤 별도 평가한다. 기관명 일치가 커리큘럼 일치를 압도하지 않는지도 확인한다.

Nori/동의어/필드 매핑 변경은 재색인 필요 여부를 확인하고 새 물리 색인을 만든 뒤 검증→별칭 전환한다. 쿼리 필드 boost만 바꾸면 일반적으로 데이터 재적재 없이 새 쿼리에 반영할 수 있으나 현재 구현은 Python 코드 변경 및 서버 재시작이 필요하다. 동의어 hot reload/외부 가중치 설정 서비스는 아직 없다.

Elasticsearch `_explain` 또는 explain 검색은 특정 결과의 점수 근거를 조사할 때만 사용한다. 모든 사용자 요청에서 실행해 로그를 늘리지 않는다. 문서 수와 색인이 달라지면 BM25 점수도 바뀌므로 서로 다른 실행의 절대 score 숫자를 곧바로 비교하지 않는다.

클릭/선택은 상단 노출 편향을 받는다. 미클릭을 무관으로 확정하거나 선택을 취업/수강 성공으로 간주하지 않는다. LLM 답변의 긍정 표현·자기 평가를 만족도 라벨로 사용하지 않는다. 기록이 충분할 때 Learning to Rank/리랭커 도입을 검토하며 지금 자동 학습을 구현한 것은 아니다.

## 다음 구현: 사용자 행동 이벤트

노출(impression) → 카드 선택(select) → 원문 클릭(open_source) → 재검색(reformulate) → 명시적 피드백(feedback)을 request_id·노출 순위·source+ID·검색 설정 버전으로 연결할 계획이다. 미선택은 부적합 확정이 아니며 실제 노출 여부와 위치 편향을 함께 확인한다. 충분한 표본 전에는 수동 검토 후 가중치를 조정한다. 이 이벤트 수집과 자동 순위 학습은 아직 구현하지 않았다.
