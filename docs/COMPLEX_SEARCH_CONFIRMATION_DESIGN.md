# 복합 검색과 검색 설명·사용자 확인 설계

확정일: 2026-11-02. 상태: **사용자 합의에 따른 구현 방향 확정 / 구현·운영 배포 전**.
기존 검색 문맥·추천 근거 계획을 구체화한다. 이 문서의 예시 JSON은 새 계약 초안이며 현재 운영 API 형식이 아니다.

## 1. 고정한 결정

- SearchPlan에 한정해 Pydantic 검증을 도입하는 방향으로 진행한다. 프로젝트 전체 스키마 전환은 범위 밖이다.
- Bedrock은 사용자 의도를 정해진 JSON으로 분류하고, 서버가 검증·정규화한 뒤 검색식을 만든다. 모델의 임의 SQL/DSL은 실행하지 않는다.
- 지역·직무의 대안과 보유 역량·명시적 필수 조건을 구분한다. 단순 프롬프트 수정만으로 완료하지 않는다.
- 복합 요청은 **조건 해석 → 실제 검색 → 검색 설명·사용자 확인 → 공고 표시**로 진행한다.
- 검색 설명은 실제 실행 계획·건수에 근거한다. 모델이 임의로 조건 제외나 검색 성공을 주장하지 않는다.
- 간단하고 명확한 즉시 표시 요청은 확인 단계를 생략할 수 있다. 복합 요청·조건 변경에는 확인 단계를 적용하고, 0건은 조건 변경 제안으로 안내한다.
- 지역 OR는 한 번의 검색으로 처리한다. 모델 호출 한도를 무작정 늘리거나 지역마다 모델을 반복 호출하지 않는다.
- 임베딩은 이번 선행 작업이 아니다. 구조 수정 후 의미 표현 차이로 인한 누락을 검증하고 별도로 도입 여부를 결정한다.

## 2. 검색 계획 계약 초안

```json
{
  "target": "jobs",
  "regions": ["부산", "경남"],
  "roles": ["백엔드", "데이터 엔지니어링"],
  "owned_skills": ["Python", "C", "C++", "AWS", "EC2"],
  "required_skills": [],
  "preferred_skills": [],
  "career": {"levels": ["entry", "junior"], "max_years": null},
  "limit": 5
}
```

| 구분 | 실행 의미 |
|---|---|
| regions | 목록 내 OR. 경남/경상남도 등 주소 표기를 정규화하고 사용자 지역 제한을 유지 |
| roles | 목록 내 OR. 직무 제목·주요업무 등 관련 필드 활용 |
| owned_skills | 보유 경험. 관련성·순위에 활용하며 전부 필수인 AND로 만들지 않음 |
| required_skills | 사용자가 공고에 반드시 있어야 한다고 명시한 조건만 AND 적용 |
| preferred_skills | 희망 검색 선호. 공고 자체의 우대사항과 다른 개념 |
| career | 희망 경력 범위. 주니어를 임의의 연수로 치환하지 않으며 정보 부족은 미확인 |
| target | 채용/교육 검색을 구분. 교육은 별도의 과정·일정 조건 계약을 연결 |

지역 그룹과 직무 그룹, 명시적 필수 조건 그룹 사이에는 AND를 적용한다. 보유 기술의 개별 일치 수·검색 필드 등 순위 규칙과 정확한 가중치는 테스트 후 결정한다. 기술이 전혀 맞지 않는 후보를 어디까지 허용할지도 별도 평가하며 무조건 전체 공고를 관련 후보라고 부르지 않는다.

컴퓨터공학 전공·FFI 연동 등 경험 원문은 사용자 발언 참조와 함께 보존한다. 검색 태그로 표현하지 못한다고 원문 경험을 삭제하지 않는다. 보유 경험을 자동으로 자격 충족으로 판정하지 않는다.

Pydantic은 추가 필드 거부, 엄격한 타입·길이·개수·연수·limit 제한과 오류 위치 확인에 사용한다. 의미 판정은 프롬프트·서버 정책·회귀 테스트 책임이다. 기술 별칭은 버전 관리하며 C/C++/C#, Angular/AngularJS를 무분별하게 합치지 않는다.

## 3. 검색 설명과 확인 화면

검색 후 공고 카드를 바로 내보내기 전에 다음을 표시한다.

> 부산 또는 경남의 백엔드·데이터 엔지니어링 후보를 검색했어요. 현재 검색 기준 후보는 N건입니다.
> 지역·직무는 검색 조건으로 적용했고, Python·C/C++·AWS 경험은 관련성 정렬에 활용했어요.
> 전공·FFI 경험은 필수 필터로 제한하지 않았어요. 신입·주니어 지원 가능 여부는 공고별 경력 요건 확인이 필요해요.
> [이 기준으로 공고 보기] [조건 수정]

N은 실제 조회·가시성 정책을 반영한 값만 사용한다. 모델이 예시 숫자를 만들지 않는다. ES 총건수와 최신 MySQL 검증 후 표시 가능 건수가 다르면 구분해 안내하고 검증하지 않은 전체 결과를 전부 검증했다고 표현하지 않는다.

‘조건을 뺐다’ 대신 ‘필수 필터로 제한하지 않고 관련성에 활용했다’처럼 실제 처리를 설명한다. 필수 조건을 결과 확보 목적으로 조용히 완화하지 않는다. 0건이면 수행 조건·자료 범위를 설명하고 사용자가 선택한 변경만 적용한다.

조건 수정은 변경한 선호만 갱신한다. ‘지역 상관없어’는 지역 제한 해제이며 과거 조건을 계속 누적하지 않는다. 사용자가 역량 문답을 거절한 상태도 유지한다.

## 4. 저장·재사용과 최신성

- 서버가 검색 식별자, 사용자 발언 참조, 모델 원본 계획, 검증·실행 계획, 조건 역할, 규칙 버전, 실제 검색 backend, 조회 시각, 건수 의미, 상위 후보 참조·출처 버전을 기록한다.
- 공고 보기에는 같은 검색 식별자와 확정된 조건 버전을 전달한다. 단순 확인 클릭 때문에 Bedrock을 다시 호출하거나 무관한 검색을 새로 수행하지 않는다.
- 표시 직전 MySQL에서 후보의 현재 노출·마감·버전을 확인한다. 변경으로 목록이 달라지면 사용자에게 알리고 필요한 경우 같은 조건으로 재조회한다. 검증 전 후보 참조와 실제 표시한 추천 근거를 구분한다.
- MySQL을 대화·검색 근거의 기준 저장소로 사용한다. 기존 JSON/근거 테이블 재사용과 별도 검색 실행 테이블의 필요성을 구현 전에 비교한다. 이 문서는 DDL 생성 승인이 아니다.
- 같은 소유자·유효 세션만 조회하며 현재 세션 만료 정책을 따른다. 캐시는 검색 조건·정책·후보 버전을 포함하고 재시도 중복을 막는다.
- 후속 ‘왜 추천했어?’에는 실제 저장된 사용자 발언·일치 필드·실행 조건을 이용한다. 내부 추론을 저장하거나 사후에 이유를 꾸미지 않는다.

## 5. 구현 순서와 완료 기준

1. 기존 dataclass/SearchPlan 사용처·의존성·저장 세션과 캐시를 조사하고 Pydantic 검색 계약과 이전 형식 호환 규칙을 확정한다.
2. Bedrock 출력 프롬프트와 검증·정규화를 함께 변경한다. 학력·경력·지역·직무와 기술을 분리한다.
3. Elasticsearch와 MySQL 복귀 경로가 같은 AND/OR·지역·필수/선호 의미를 따르게 수정한다. 순위 차이와 지원하지 않는 조건은 명시한다.
4. 검색 설명·확인 대화 상태와 화면, 검색 참조 저장·근거 조회를 구현한다. 자연어 확인/수정과 버튼 중복·이전 검색 버튼 클릭도 검증한다.
5. AWS/Bedrock 호출 없는 테스트부터 수행한 뒤 opt-in 소량 모델·운영 검증과 배포를 별도로 진행한다.

필수 회귀 사례:
- 부산이나 경남 + 백엔드/데이터 + Python/C/C++/FFI/AWS/EC2 경험 + 신입~주니어의 긴 원문 요청.
- React/Vue/Angular 보유 경험과 ‘모두 필수’ 요청의 다른 검색 의미.
- 부산만 요청, 지역 제한 해제, 기존 희망 직무 유지와 변경.
- 채용에서 교육으로 전환, 역량 질문 거절 유지.
- 실제 지역 후보 부족, 잘못된 JSON, 사용자에게 설명한 조건과 실행 조건 일치.
- 확인 전 카드 미표시, 확인 후 저장 검색 재사용, 수정 후 이전 검색 참조 차단, 마감/버전 변경·소유자 격리·만료·재시도.

검색 건수 증가만으로 개선 완료라 하지 않는다. 계획 해석·설명 일치·필수 조건 보존·관련성·지연·호출량을 함께 검증한다. 고정 스냅샷 결과를 현재 모집 상태나 합격 가능성으로 표현하지 않는다.
