# AI 질문 선정 평가 계획

상태: 평가 설계 / 질문 선정 기능 로컬 구현 완료·정답셋/실모델 평가 미실행
기준일: 2026-11-02

## 목적과 범위

공고 선택 시 Bedrock이 원문 조건을 읽고 ask/reference/review로 분류해 불필요한 문답을 줄이되 중요한 지원 요건을 생략하지 않는지 평가한다. 사용자 지원 자격·실무 역량·합격 여부를 평가하는 기능이 아니다. 기존 대화 의도 분류 v3 평가와 별개이며 고용24 승인 전 현재 데이터로 시작할 수 있다.

원문·항목 ID·공고 버전은 서버가 보존한다. 모델은 분류와 짧은 관측 가능한 이유만 반환한다. 원문 삭제·재작성이나 질문 제외 항목의 충족 처리는 금지한다. 검토 결과는 조건 원문 해시와 정책/프롬프트 버전으로 저장해 재사용하는 방향이다. 주소·마감일만 바뀌면 조건을 재검토할 이유가 없다. 아직 이 기능이 구현됐다는 뜻은 아니다.

## 정답 정책

| 라벨 | 기준 | 예시 |
|---|---|---|
| ask | 사용자 확인이 필요한 구체적 요건 | 관련 경력 3년 이상, 자격증 필수 |
| reference | 질문 대신 안내할 내용 | 학력무관 |
| review | 의미·경계가 애매해 자동 생략하지 않을 내용 | 제한 없음과 필수 조건이 혼합된 항목 |

책임감·열정·성장 의지를 일률적으로 무의미하다고 취급하지 않는다. 기본 문답에서 참고사항으로 돌릴지 제품 정책을 먼저 정한다. 사람 판단이 다르면 이유를 기록하고 합의되지 않은 항목은 review로 둔다. 중요한 조건이 들어 있는 복합 항목 전체를 reference로 보내면 오생략이다. review 항목은 숨기지 않고 원문 확인 대상으로 유지한다.

## 표본과 라벨링

초기 목표는 공고 30개, 조건 약 200~300개다. 실제 조건 수를 집계하고 부족하면 공고를 보충한다. 필수/우대, 직무, 학력·경력·기술·면허·성향, 간단/복합/목록형 문장을 나눠 선정한다. 현재 점핏 중심 표본의 결과를 의료 등 미포함 직군에 일반화하지 않는다.

사람이 원문을 보고 condition_id, 원문 참조/해시, 정답 라벨, 이유, 중요 조건 여부를 기록한다. 가능하면 2명이 독립 라벨링한 뒤 불일치를 조정한다. 한 명만 검토했다면 그 한계를 명시한다. 원문 전체의 누락 여부와 이미 분리된 조건의 선정 품질을 별도로 확인한다.

공고 단위로 개발용 약 20개와 최종 평가용 약 10개를 분리한다. 같은 공고/유사 재등록본의 조건이 양쪽에 섞이지 않게 한다. 프롬프트는 개발용으로만 조정하고 최종 평가용을 본 뒤 수정하면 별도 평가셋을 다시 확보한다. 모델 출력 전에 정답과 중요 조건을 고정한다.

## 필수 함정 사례

- 학력무관, 단 관련 자격증 필수: 항목 전체 생략 금지.
- Python 또는 R 사용 가능: 대안 관계 유지, 둘 다 필수로 바꾸지 않음.
- 경력무관과 관련 경험 필수가 함께 있는 공고: 모순/범위 확인.
- 제목·하위 목록·괄호·이어지는 문장: 항목 경계가 깨져 조건이 누락되는지 확인.
- 학위·면허·경력과 성향이 섞인 문장: 객관적 요건이 성향 분류에 묻히지 않음.
- 원문 안의 모델 지시문: 데이터로 취급하고 ID·출력 계약 유지.
- 모델 누락·중복 ID·알 수 없는 ID·잘린 JSON·서비스 실패: 자동 생략 없이 원문 확인으로 복귀.

실제 표본에 없는 함정은 별도 합성 사례로 표시한다. 실제 공고 성능과 합성 안전성 결과를 합쳐 실제 데이터 성능으로 제시하지 않는다.

## 지표와 분모

| 지표 | 정의 | 해석 |
|---|---|---|
| 중요 조건 오생략률 | 중요 조건 중 정답 ask인데 예측 reference인 수 / 중요 ask 전체 | 최우선. review를 화면에서 숨긴 경우도 오생략으로 별도 집계 |
| 전체 ask 오생략률 | 정답 ask인데 예측 reference인 수 / 정답 ask 전체 | 중요 요건 외의 생략도 확인 |
| 분류 일치율 | ask/reference/review 정답과 일치한 수 / 전체 조건 | 3×3 혼동행렬과 라벨별 결과를 함께 보고 |
| 불필요 질문 잔존율 | 정답 reference인데 예측 ask인 수 / 정답 reference 전체 | 과도한 질문이 얼마나 남는지 |
| review 비율 | 예측 review 수 / 전체 조건 | 전부 review로 보내는 회피를 탐지 |
| 유효한 질문 감소율 | 기존 기본 질문 수 대비 최종 질문 수 감소 비율 | 오생략 지표를 함께 제시해야 함 |
| 원문 연결 오류 | 누락·중복·없는 ID·원문 연결/버전 불일치 수 | 서버 검증 전 원시 출력과 검증 후 결과를 구분 |
| 반복 일관성 | 동일 조건의 3회 라벨 일치율 및 중요 오생략 발생 횟수 | 평균만으로 단발성 오생략을 숨기지 않음 |
| 운영 비용·지연 | 최초 검토 입력/출력 토큰, 실패·재시도, 경과 시간 p50/p95 | 소표본 p95의 한계와 표본 수 명시 |
| 결과 재사용 | 동일 해시/정책의 모델 재호출 수, 변경 시 재검토 여부 | 캐시 적중과 오래된 분류 재사용 오류 구분 |

분모가 0인 지표는 N/A로 보고한다. 모델/형식 실패를 성공 표본에서 빼서 일치율을 부풀리지 않는다. 원시 실패율과 fallback 적용 후 서비스 결과를 별도로 보고한다. AI 이유의 원문 부합 여부도 사람이 확인하되 내부 사고 과정은 수집하지 않는다.

## 초기 통과 기준

다음은 운영 적용을 위한 초기 제안 기준이며 측정 결과가 아니다.

- 원문 연결 오류는 최종 서비스 결과에서 0건. 원시 오류는 차단 여부와 함께 모두 보고.
- 사전에 지정한 중요 조건의 오생략은 최종 평가와 반복 시험에서 0건.
- 모델/검증 실패·누락·모호한 항목은 자동 생략하지 않고 review/원문 확인으로 유지.
- 전체 조건을 review로 보내는 결과는 안전성만 통과했다고 볼 수 있으며 실용적 개선 통과가 아님.
- 일반 일치율·질문 감소율·비용·지연 목표는 개발 표본의 기준선 확인 후 최종 평가 전에 고정. 수치가 미정이면 미정으로 표시하며 종합 통과를 선언하지 않음.

표본에서 중요 오생략 0건이어도 전체 공고에서 무오류라는 보장은 아니다. 최종 평가 표본 수와 각 분모를 반드시 함께 공개한다.

## 실행 순서와 산출물

1. 분류 정책·애매한 사례 처리 합의.
2. DB 스냅샷에서 공고·조건 추출 및 원문 대조, 사람 정답 작성.
3. 공고 단위 개발/평가 분리와 데이터·정답 해시 고정.
4. 스키마·ID·누락·실패 복귀 단위/통합 테스트.
5. 개발 표본으로 프롬프트 조정 후 버전 고정.
6. 실제 Bedrock으로 미사용 평가 표본을 반복 평가. 모델 ID/리전·정밀 설정·프롬프트·정책·원문 해시·호출 시각·usage·실패를 기록.
7. 기존 전체 질문 방식과 같은 조건으로 비교하고 실패 사례 검토.
8. 비교 운영: AI 결과만 기록하고 사용자 질문 목록은 그대로 유지.
9. 통과 기준 확인 후 소량 적용, 원문과 참고사항 공개·되돌리기 유지.

산출물은 manifest, 사람 labels, 모델 predictions, metrics/혼동행렬, 실패 검토, 전후 비교 보고서다. 평가 코드와 비공개 표본은 서비스 실행 코드·수집 원본과 분리한다. 실제 원문·사용자 대화·비밀값을 무조건 Git에 올리지 않는다. 저장 위치와 보존 정책은 평가 구현 시 정한다.

## 현재 완료 여부

이 문서는 평가 항목과 실행 계획만 고정한다. 질문 선정·저장·ES 연결은 로컬 구현 및 무결성 검증을 마쳤다. 30개 공고 정답셋, 실제 모델 평가, 선정 품질 수치, 운영 적용은 아직 완료하지 않았다. 기존 문맥 분류 48개 모의 실행 테스트를 이 기능의 선정 정확도 증거로 재사용하지 않는다.
