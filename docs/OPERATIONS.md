## 2026-10-29 Elasticsearch 도입 합의와 구현 상태

이 절은 아래 과거 초안의 검색엔진 관련 설명보다 우선한다. **로컬 Nori·동의어 실행과 실제 스냅샷 783건 색인·검색 어댑터 검증을 완료했으며 운영 Elasticsearch는 미도입이다.** 직접 설치 방식으로 진행하며 OpenSearch·Elastic Cloud로 자동 대체하지 않는다. 로컬 Docker에서 분석기·색인·백엔드·동기화를 검증한 뒤 AWS에 배포한다. S3는 원본·백업 저장소이며 검색엔진 설치 위치가 아니다.

소비자는 DB 반영된 Outbox만 처리한다. source+ID와 버전으로 중복·역순 이벤트를 처리하고 색인 성공 확인 후 완료 표시한다. 실패 재시도·실패 이력·적체량·최종 동기화 시각을 관찰한다. 신규뿐 아니라 수정·마감·삭제/노출 중단도 반영한다. 초기 전체 색인과 증분의 경계에서 이벤트가 누락되지 않도록 체크포인트를 설계한다.

로컬 재시작 후 색인 유지, 전체 재생성, 별칭 복귀, 검색 어댑터 SQL 복귀를 검증한 뒤 AWS에 올린다. 운영 색인과 DB를 동시에 삭제하지 않는다. 상세 절차는 [도입 계획](ELASTICSEARCH_ROLLOUT.md)을 따른다.

## 주기적 동기화

원본 출처가 웹훅을 제공하지 않으면 실시간 감지를 보장하지 않는다. 초기 제안은 몇 시간 간격의 목록 확인과 하루 한 번 전체 대조이며, 출처 허용 범위와 데이터량으로 확정한다.

목록 → 신규/변경 후보 → 상세 확인 → S3 원본 → 검증 → DB upsert와 Outbox 기록 → 전달 → Elasticsearch 갱신.

목록에 수정 시각이 없으면 알려진 활성 공고 상세도 순환 확인한다. 목록에서 한 번 누락됐다는 이유로 삭제하지 않는다. 명시적 마감, 마감일, 반복 확인 결과를 구분한다. 수집 실패를 전체 마감으로 처리하지 않는다.

## DB와 색인 일관성

DB를 기준으로 삼는다. 안정적 ID, 멱등 처리, 단조 증가 버전, 역순 이벤트 방지, 항목별 실패 재시도와 DLQ를 둔다. Bulk 요청은 HTTP 성공만 보지 않고 문서별 실패를 검사한다. 전송 성공과 검색 노출 완료를 구분한다. 전체 재색인과 불일치 대조 절차를 마련한다.
