# Elasticsearch 직접 설치 도입 순서

## 2026-10-30 현재 적용 상태 (아래 과거 기록보다 우선)

기존 EC2를 t4g.medium(4GiB)으로 확장하고 ARM64 Elasticsearch 9.5.5·Nori를 설치했다. 동일 인스턴스와 EBS를 유지했으며 MySQL 채용 942건·교육 7건을 별도 색인에 반영했다. 엔진 green, 작업자 active, 검색 포트는 127.0.0.1:19200으로 제한한다. 16:09 측정 시 가용 메모리 약 2207MiB이며 부하 시험 결과는 아니다.

운영 챗봇의 검색 경로는 아직 MySQL이다. 최신 연결 코드·검색 선택 설정 적용, 운영 복귀 검증과 Outbox 자동 소비는 남아 있다. 실패 입력 선저장 보완도 로컬 검증 상태이며 운영 앱에는 배포하지 않았다. CloudFormation LaunchTemplate의 기존 t4g.small 설정은 실제 크기와 달라 후속 인프라 변경 전 안전한 정합화가 필요하다.

상세 실행·검증 기록: [AWS 검색 배포 결과](../infra/elasticsearch/DEPLOYMENT_20261030.md). 아래 날짜별 내용은 당시 이력으로 읽는다.


## 2026-10-29 초기 AWS 서버 배치 확정

초기는 기존 EC2를 확장해 MySQL·백엔드 작업자·Elasticsearch를 한 서버에서 함께 운영한다. 신규 검색 전용 EC2는 초기 배포에 추가하지 않는다. 이 결정은 과거의 서버 배치 미정 설명보다 우선한다. 인스턴스 유형·메모리·디스크·월 차액·점검 시간은 아직 미정이며 실제 크기 변경은 실행하지 않았다.

검색 포트는 외부에 공개하지 않고 같은 서버 내부로 연결한다. 검색 읽기/색인 쓰기 권한과 비밀 설정, 영속 볼륨·재시작 정책을 준비한다. 자원 제한으로 DB·작업자에 미치는 영향을 줄인다. 지속적인 메모리 압박/OOM, 검색으로 인한 DB 응답 악화, 색인 지연 또는 독립 배포·복구 필요가 확인되면 검색 전용 EC2 분리를 검토한다. 분리 수치 기준은 관측 후 정하며 정식 부하 검증은 고용24 파이프라인 단계로 이관한 합의를 유지한다.

작성일: 2026-10-29. 이 문서는 구현 계획이다. 현재 운영 검색은 MySQL이다. 기본 비교 실험에 이어 로컬 Nori 이미지 실행·엔진 내부 기술 동의어·기술명 구분·출처 ID 분리의 합성 검증을 완료했다. 실제 공고 색인과 서비스 연결은 미완료다.

## 파일 배치 계획

```text
app/backend/src/repositories/elasticsearch_jobs.py  # 검색 어댑터
app/ingestion/search_index/                        # 전체 색인·Outbox 소비·재시도
infra/elasticsearch/Dockerfile                     # Nori 포함 이미지
infra/elasticsearch/compose.local.yaml             # 로컬 실행·볼륨
infra/elasticsearch/config/                        # 매핑·분석기·동의어
docs/SEARCH_QUALITY_EXPERIMENT.md                   # 기존 실험 방법
```

전용 새 app 서비스는 추가하지 않는다. infra/elasticsearch의 Dockerfile·compose.local.yaml·config/jobs.local.json·verify_local.py는 2026-10-29 생성했다. backend 어댑터와 ingestion 소비자는 아직 생성하지 않았다. infra는 실행 환경, ingestion은 데이터 반영, backend는 사용자 검색을 담당한다.

## 1. 로컬 실행 환경 준비

호환되는 Elasticsearch·analysis-nori 버전을 고정하고 Docker 이미지를 만든다. 로컬 포트는 기존 MySQL·실험 포트와 충돌하지 않게 정한다. 색인용 영속 볼륨과 메모리 한도를 설정한다. 운영 인증정보를 복사하지 않는다.

통과 기준: 엔진과 Nori 로드 확인, 재시작 후 데이터 유지. 공개 스냅샷의 루프백 전용 실험 설정을 운영 보안 설정으로 재사용하지 않는다.

## 2. 매핑·한국어 분석 설정

제목·본문은 텍스트 분석, 기술명·식별자·상태는 정확 일치가 가능하게 설계한다. Nori가 동의어를 자동 이해하는 것은 아니다. 기술명 보존 규칙과 명시적 동의어를 별도로 정의하고 분석 API로 실제 토큰을 확인한다. 필드별 검색 분석기와 색인 분석기의 호환성을 검증한다.

통과 기준: C++/C#/Next.js가 엉뚱한 기술과 합쳐지지 않고 리액트/React 등 등록한 별칭만 의도대로 연결된다. Python 전처리와 엔진 동의어의 중복 적용도 점검한다.

## 3. 전체 색인과 품질 평가

고정 스냅샷을 source+ID·버전과 함께 색인한다. SQL/동의어 SQL/설정된 Elasticsearch를 같은 조건으로 비교한다. 초기 실험은 783건·질의 18개·사람 평가 후보 178쌍으로, standard 분석기와 Python 별칭 처리만 사용했다. Nori·엔진 동의어 검증 결과가 아니다.

통과 기준: 기술·지역·상태·마감 필터 정확성, 사람이 판정한 P@5·nDCG@5와 누락 사례 검토. 평가 전후 데이터와 질문 버전을 보관한다. 튜닝에 쓰지 않은 질문으로 재검증한다.

## 4. 로컬 백엔드 연결

Bedrock의 검증된 SearchPlan을 서버가 DSL로 변환하도록 어댑터를 추가한다. API Gateway/Lambda/SQS 구조를 바꾸는 작업이 아니라 기존 EC2 작업자의 검색 구현 교체다. 검색 결과 ID·버전을 기준 DB에서 확인한다. 원본 전체를 Bedrock에 전송하지 않는다.

통과 기준: 자연어→계획→검색→카드→조건 확인까지 실제 화면에서 검증. 0건과 장애를 구분하고 설정으로 SQL 경로로 복귀 가능해야 한다.

## 5. 증분 동기화와 복구

DB+Outbox를 기준으로 신규·수정·마감·삭제/노출 중단을 색인에 반영한다. 최신 버전이 과거 이벤트로 덮이지 않도록 하고 성공 후에만 완료 처리한다. 재색인 시 변경분 경계를 기록해 누락을 방지한다.

통과 기준: 중복·역순·중간 실패·재시도·소비자 재시작, 적체 감시, 새 색인 검증 후 별칭 전환과 이전 색인 복귀, MySQL 기반 재생성.

## 6. 용량과 비용 결정

데이터는 최소 현재 규모 3배 증가를 고려한다. 실제 데이터가 부족하면 부하용 복제 문서는 별도 색인·별도 ID로 명시하고 관련성 평가에 섞지 않는다. 색인 크기·RSS/힙·CPU·디스크·동시 검색 지연을 측정한다.

기존 t4g.small 2GB에는 무조건 함께 설치하지 않는다. 기존 EC2 확장과 검색 전용 EC2 추가의 전체 비용/차액을 비교하고 운영 시간도 반영한다. EBS·백업·로그·네트워크와 별도 Bedrock 토큰 비용을 포함한다. 서버 크기·월 금액은 아직 미정이다.

## 7. AWS 배포와 확인

검증된 이미지·설정을 사용하되 현재 EC2의 ARM 아키텍처 호환성을 확인한다. 검색 포트는 인터넷과 브라우저에 공개하지 않는다. 서버 간 권한·인증·통신 보호·영속 저장소·재시작 정책을 준비한다. S3는 원본/백업 저장소이고 Elasticsearch 실행 서버가 아니다.

수동 소량 색인→실제 검색→증분 반영→장애 복구 순으로 확인 후 전환한다. 유료 자원 생성 전에 실제 견적과 배포 변경 내용을 검토한다. 로컬 비교 실험 완료를 운영 도입 완료로 발표하지 않는다.


## 2026-10-29 실제 스냅샷 색인 진행

783건 로컬 색인과 ElasticsearchJobRepository 검색 검증을 완료했다. app/ingestion/search_index/README.md를 따른다. backend 검색 어댑터 파일은 생성했지만 bootstrap에는 미연결이다. Outbox 소비자와 운영 DB 최신 상태 재검증은 미구현이다. 백엔드 145개 테스트를 실행해 7개 환경 의존 테스트 제외 통과했다. 기존 실험과 날짜가 달라 결과 건수의 직접 개선 비교는 하지 않는다.


## 로컬 대화 연결 후속 상태

2026-10-29 로컬 JOB_SEARCH_BACKEND 선택과 검색 후보 MySQL 상태·마감·버전 확인을 연결했다. 상세는 LOCAL_ELASTIC_CHAT.md 참조. 운영은 MySQL 검색 그대로다. 4번 부하 검증은 사용자 요청으로 고용24 데이터 파이프라인 단계로 이관했으며 통과한 것으로 처리하지 않는다. 로컬 서비스 계층 검증은 완료했지만 실제 브라우저 자연어 테스트와 자동 증분 소비자는 남아 있다.

## 2026-10-30 합의: 자동 동기화와 마감 공고 노출

아래는 확정한 처리 방향이며 이번 문서 수정으로 작업자·스케줄·운영 설정을 실행한 것은 아니다. 현재는 DB 변경과 Outbox 기록, 수동 전체 색인까지 구현했고 자동 소비자는 미구현이다.

- MySQL을 원본으로 보관하고 Elasticsearch는 재생성 가능한 검색용 사본으로 운영한다. 신규·수정·모집 종료·삭제/노출 중단 변경은 DB와 같은 트랜잭션의 Outbox를 통해 전달한다.
- 초기 자동 소비 주기는 1분을 목표로 한다. 수집 주기와 별개이며 처리 시간·장애로 실제 지연이 늘 수 있으므로 실시간 보장은 하지 않는다. 작업자는 성공한 이벤트만 완료 처리하고 실패 시 지연 재시도하며 반복 실패·적체를 관측한다.
- source+source_id와 단조 증가하는 버전을 기준으로 중복 처리·역순 도착을 견딘다. 삭제/노출 중단도 검색 문서 제거 또는 비노출 처리로 반영하며 원본의 물리 삭제와 구분한다. 소비 권한은 대화용 계정과 분리한다.
- 마감일이 경과한 공고는 사용자 검색에서 즉시 제외한다. Elasticsearch 필터와 최종 MySQL 재확인을 함께 사용하고 MySQL 복귀 검색에도 같은 시간·상태 기준을 적용한다. 이미 표시된 카드의 선택·상세 확인 시에도 재확인한다.
- 날짜 경과는 새 수집 이벤트 없이도 발생하므로 별도 주기 작업이 기한 경과를 탐지해 노출 상태를 갱신하고 필요한 Outbox 이벤트를 생성한다. 이 작업의 실행 간격은 구현 시 정한다. 검색 시 필터가 동기화 지연 동안의 노출을 막는다.
- 마감일 경과에 따른 노출 제외와 원문에서 직접 확인한 모집 종료는 별도 근거로 기록한다. 날짜가 지났다는 이유만으로 원문 확인 시각이나 실제 종료 확인을 만들어내지 않는다. 기존 원문·이력은 MySQL에 보관한다.
- 정확한 마감 시각은 출처 시간대를 적용한다. date_only는 원문 날짜·정밀도를 유지하고 한국 날짜 기준 해당 날짜가 지난 뒤 제외한다. 이는 노출 정책이지 실제 마감 시각 추정이 아니다. 날짜 없음·상시채용·상태 미확인은 모집 중으로 단정하지 않으며 정기 원문 재확인 대상으로 둔다. 조기 마감은 출처 재확인으로 탐지한다.

구현 완료 기준: 신규·수정 자동 반영, 중복/역순 이벤트, 실패 후 재시도, 마감 날짜 경계, 조기 마감, 상시/미확인, 검색 장애 시 동일 필터 유지, 원본 보존, 재색인 후 변경 누락 방지를 검증한다. 운영 검색 전환과 자동 동기화 배포는 후속 작업이다.
