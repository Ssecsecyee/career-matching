## 3. 검색 정책 변경

1. 희망 직무·지역 등 명시적 검색 선호를 세션에 구조화해 유지한다. 현재 발화에 다시 없다고 삭제하지 않는다. 사용자가 바꾸거나 해제하면 갱신하며, 과거 기술을 무조건 필수 조건으로 누적하지 않는다. 사용자 발언 출처를 함께 보관한다.
2. 보유 역량과 공고에 반드시 있어야 한다고 요청한 조건을 분리한다. 세 기술을 모두 보유했다는 말이 세 기술을 모두 사용하는 회사만 원한다는 뜻은 아니다.
3. 보유 기술은 적어도 하나의 관련 기술 일치와 직무 관련성으로 후보를 찾고, 일치 개수·일치 위치 등으로 순위에 반영하는 방향을 검증한다. 사용자가 공고 조건으로 '전부 필수'를 명시한 경우에만 해당 AND 제한을 적용한다. 필수 조건을 결과 수 확보를 위해 조용히 완화하지 않는다.
4. VueJs/vuejs/Vue.js 같은 표기와 기술의 버전·계열을 구분해 매핑한다. Angular와 Angular 2 대조 성공은 AngularJS까지 같은 기술로 합쳐도 된다는 근거가 아니다. 출처 태그는 보존하고 검색용 정규화·확장 규칙을 별도로 관리한다.
5. 프론트엔드 목표를 보존한 직무 제한/우선순위와 기술 관련성 순위를 함께 검증한다. OR 전환만으로 품질 개선 완료를 주장하지 않는다. 가중치는 실험으로 결정하며 최적값으로 미리 확정하지 않는다.
6. 검증된 SearchPlan 계약에 선호·필수 조건·조합 의도를 표현하고 서버가 DSL로 변환한다. 모델이 임의 SQL/DSL을 실행하지 않는다. MySQL 복귀 경로도 같은 검색 의미·마감 정책을 따른다.

대상 공고 55338125가 적합 후보에서 누락되는지 회귀 검사한다. 보유 기술만으로 경력 요건 충족이나 지원 가능성을 보장하지 않으며 해당 공고를 항상 1위로 강제하지 않는다.

## 4. 저장 책임과 위치

저장·권한·조회는 백엔드가 담당하고 AWS의 기존 EC2 MySQL을 사용한다. Bedrock 자체 대화 기억이나 Elasticsearch 문서에 사용자 추천 근거 원본을 맡기지 않는다.

| 기존 테이블 | 활용 방향 및 추가 작업 |
|---|---|
| chat_messages | 사용자 원문·최종 응답, message_id와 request_id 기반 참조. 수신·실패 이력과 최종 추천을 구분 |
| chat_sessions | 명시한 희망 직무·검색 선호·선택 대상·질문 허용 여부 및 근거 조회용 최근 표시 대상 참조. 현재 profile/requirement_answers JSON 활용 가능성 검토 |
| recommendation_evidence | 기존 조건 자기평가 근거를 유지하고 검색 후보 제시 근거 유형과 저장 경로를 추가 |

현재 recommendation_evidence에는 requirement_snapshot, user_fact_snapshot, evidence_quote, source_section, source_url, source_version, explanation, rule_version, expires_at이 있다. 하지만 현재 writer는 조건 문답의 job/check 입력만 처리한다. 검색 추천 순간의 저장·조회가 자동으로 되는 상태가 아니다.

스키마 결정은 기존 JSON 스냅샷 확장과 evidence_kind/search_context 같은 명시적 필드 또는 별도 검색 실행 테이블을 비교한 뒤 최소 마이그레이션으로 확정한다. 이번에는 DDL을 수정하지 않는다. 검색 설명을 met(충족) 자기평가로 오인하게 저장하지 않으며 조건 문답 근거와 식별 가능한 유형을 사용한다.

## 5. 검색 후보 제시 시 보관할 근거

전체 검색 결과를 모두 복제하지 않고 실제로 표시한 후보와 선택 대상을 중심으로 보관한다.

- 소유 범위·session_id·요청/최종 응답 message_id와 연결된 추천 식별자.
- 사용자가 말한 직무·기술·희망 조건의 원문 발췌와 실제 사용자 message_id. 희망과 보유·자기평가를 구분한다.
- 대상의 종류(job/program), source+source_id·DB subject_id·source_version·출처 URL.
- 실제 일치한 제목·업무·자격요건·우대조건·기술 태그와 해당 원문 스냅샷. 태그만 맞았는데 자격요건이 모두 일치했다고 설명하지 않는다.
- 원본 모델 검색 계획, 서버 정규화 후 실행 계획, 적용된 AND/OR·필수/선호 구분 및 버전. 저장량을 제한하고 비밀정보는 포함하지 않는다.
- 실제 조회 backend(Elasticsearch/MySQL 복귀), 표시 순위·관측 점수·검증된 일치 특징, 검색/분석기/동의어/가중치 규칙 버전. 점수만으로 합격 가능성을 해석하지 않는다.
- 학력·경력 등 미확인 사항과 추천 한계, 사용자에게 제시한 짧은 설명. 모델 내부 추론 과정 대신 출처로 확인 가능한 설명을 보관한다.

최종 응답과 근거를 같은 저장 단위로 확정하고, 저장 실패·재시도 시 중복 근거를 만들지 않는다. 응답 캐시에는 근거 참조와 정책·선호·대상 버전을 연결해 서로 다른 검색 맥락의 설명을 재사용하지 않는다. 실제 조회와 다른 사후 설명을 만들어 저장하지 않는다.

## 6. '왜 추천했어?' 후속 처리

1. 질문이 새 공고 검색인지, 이미 표시한 대상의 추천 이유 질문인지 구분한다.
2. 현재 선택 대상, 직전 표시 목록, 사용자가 지정한 이름/순번과 메시지 참조로 대상을 해석한다. 모호하면 어느 대상인지 확인한다. 채용·교육 목록을 혼동하지 않는다.
3. 같은 소유자·유효 세션에 속한 추천 근거와 참조한 사용자 발언을 MySQL에서 읽는다. 최근 몇 턴의 모델 문맥에서 밀려났어도 유효한 근거 기록은 조회한다.
4. 필요한 발언·근거·미확인 조건만 제한된 모델 문맥으로 전달한다. 모든 대화를 매번 전송하거나 사용자에게 이미 말한 경험을 반복 질문하지 않는다.
5. '앞서 React 경험과 프론트엔드 희망을 말했고, 이 공고의 어떤 기술/직무 조건과 연결됐다. 경력 요건은 미확인이다'처럼 답한다. 검색 일치와 자격 충족을 구분한다.
6. 공고가 바뀌거나 마감됐으면 추천 당시 스냅샷과 현재 상태를 구분한다. 질문 거절을 유지하고 조건 확인을 강제로 재개하지 않는다.

기존 기록이 있는데 일괄적으로 '알 수 없다'고 답하지 않는 것이 목표다. 다만 과거 추천에 구조화된 근거가 없거나 기록이 만료·삭제됐으면 그 한계를 구체적으로 밝힌다. 당시 검색 이유를 현재 데이터로 꾸며 복원하지 않는다. 이전 추천에 근거가 소급 생성됐다고 주장하지 않는다.

## 7. 보관·격리·운영 기준

- 현재 운영 대화의 24시간 세션 만료 정책을 따른다. 새 추천 근거는 기존 세션 expires_at을 이어받고 매 생성 시 만료를 연장하지 않는다. 장기 보관·분석 보관 기간은 미정이다.
- 만료 후 조회 차단과 실제 물리 삭제는 별개다. 근거·대화·캐시의 정리 작업과 연쇄 삭제, 백업의 별도 보관·삭제 기간을 확인해야 한다. 24시간 후 백업까지 자동 삭제된다고 가정하지 않는다.
- 다른 세션/소유자의 추천 조회를 차단한다. 로그·Git·일반 응답에 인증값·비밀번호·다른 사용자 원문을 노출하지 않는다.
- LLM 토큰·근거 payload 크기·조회 횟수·로그 비용을 관측한다. 설정된 대화 호출 예산 안에서 불필요한 추가 모델 호출을 피한다.
- 검색 변경은 DB에 저장된 근거 정책 버전·캐시 버전과 함께 배포하고, 소량 검증 후 적용한다. 마이그레이션이 필요하면 백업·호환 읽기·이전 앱 복귀 절차를 먼저 준비한다.

| P1 | 데이터 확장 | 고용24 승인 후 소량 채용·훈련 API 매핑→격리 적재→AWS 정기 수집. 교육의 신청 후보/과거 참고 구분 유지 |
| P2 | 검색 품질 지속 개선 | 노출·선택·재검색·이유 질문 사례와 별도 사람 평가로 가중치 실험. 클릭 없음만으로 부정답 판정 금지 |

현재 0→65/66/28건 대조는 검색 완화 가능성을 보인 것이며 정확도 향상의 최종 증거는 아니다. 후보 수와 함께 P@5·nDCG@5·대상 공고 회수 여부·근거의 사실 정확성을 평가한다. 작은 소프트스킬 문구 수정에 검색이 사라지지 않는지도 검사한다.

## 9. 성능 검증 지표 생성 추가

검색 결과 수 외에 품질·추천 근거·대화 정책·속도·안정성·동기화·자원·비용 지표를 생성하는 평가기와 보고서를 추가 구현한다. 상세 정의·측정 구간·초기 통과 기준·미정 서비스 목표·데이터/산출물은 [성능 검증 계획](PERFORMANCE_EVALUATION_PLAN.md)을 따른다. 현재 지표 자동 수집/평가가 완성됐다는 뜻은 아니다. 큰 부하 검증은 고용24 단계의 별도 승인 범위로 유지한다.

## 10. 이번 문서 작업 범위

이 계획과 관련 기준 문서의 연결만 갱신한다. 구현 코드, 운영 검색 정책, 테이블·데이터, AWS 설정은 변경하지 않는다. 이번 요청에서는 Git 커밋·푸시도 실행하지 않는다. 계획 확정과 실제 구현 완료 기록을 분리한다.
