# 고용24 API 연동·DB 적재 후 검색 재검증 계획

## 1. 현재 완료와 미완료 구분

- 점핏 데이터의 MySQL 원본·버전·Outbox 기반 Elasticsearch 자동 동기화는 운영 중이다. 자체 설치 Nori와 MySQL을 기존 4GiB EC2에서 공동 운영한다.
- 최근 원본 975건 유지·출처 버전 보존을 확인했다. 11월 1일 실험 스냅샷의 노출 대상은 747건, 11월 2일 운영 확인은 날짜 경과를 반영해 MySQL/ES 각각 736건이었다. 이 수치는 해당 시각 기록이며 다음 테스트에서 재확인한다.
- 고용24 채용 API·훈련 API 실제 승인/응답과 수집 어댑터·정기 파이프라인은 아직 완료하지 않았다. 채용 승인과 국민내일배움카드 훈련과정 승인 여부를 각각 확인한다.
- 기존 점핏 수집 코드를 API 주소만 바꿔 사용하지 않는다. 출처별 응답·ID·상태·날짜·페이지 규칙을 별도 어댑터로 연결한다.
- 실험용 SQL 정규화 및 조사 제거 Nori 후보 설정은 서비스에 배포하지 않았다. 검색엔진의 의미 이해·최종 관련성·동시 사용자 처리 한도가 검증됐다는 뜻이 아니다.

본문의 실제 사례로 '시계열분석'은 '시계열 데이터 분석' 원문을 포함한 규칙 대상3건을 Nori가 회수했고, 정규화 SQL은1건을 회수했다. 반대로 공백·조사 정리만으로 SQL도 잘 처리한 조건이 많았다. Nori는 규칙 밖 추가 후보도 늘렸다. 따라서 **한국어 본문 검색에 ES 활용 가치는 확인했지만 필수성·관련성 우위가 입증됐다고 쓰지 않는다.**

단순 SQL 정규화는 소문자·공백 제거와 검색어 끝 을/를 삭제다. 품사를 구분하지 않아 일반 단어 훼손 가능성이 있으며 분야 확장 시 그대로 재사용하지 않는다. Nori도 전문용어·복합어·부정 표현을 자동으로 정확히 이해한다고 가정하지 않는다.

## 3. 먼저 완료할 API→DB→검색 연결

| 순서 | 수행 작업 | 완료 기준 |
|---|---|---|
| W0 승인 확인 | 실제 승인 서비스·공식 명세·키 전달·호출/보관/제공 범위 확인 | 채용/훈련 각각 사용할 엔드포인트와 제한을 기록. 키는 비밀 설정에만 저장 |
| W1 소량 응답 확보 | 허용 범위에서 우선 최대10건의 목록·상세 표본 수집 | 실제 ID·필드·코드·날짜·상태·페이지·오류를 확인. 없는 필드는 추정하지 않음 |
| W2 공통 형식 매핑 | source=goyong24와 source_id, 직종/지역/학력/경력 코드·원문·시간 정밀도 매핑 | source+ID 충돌 없음. 코드와 사용자 역량을 혼용하지 않음. 원본·변환 버전·누락 사유 보존 |
| W3 격리 DB 검증 | 신규/동일/변경/빈 값/마감/오래된 응답/중복/실패 시험 | 유효 값 보존, 버전 규칙, DB와 Outbox 원자성·재시도 검증 |
| W4 AWS 소량 적재 | 원본S3→적재 전용 메시지→EC2 소비자→MySQL | 백업 후 승인 표본 반영, ID·건수·필드·날짜·권한 확인. 대화용 큐와 분리 |
| W5 ES 반영·사용 흐름 | DB/Outbox→기존 동기화 소비자→출처별 ES 문서 | ID·버전·노출 정책 일치, 다른 출처 같은 ID 분리, 검색·선택·세션·캐시·근거까지 source 식별 확인 |
| W6 반복 수집 | 증분 범위·페이지·겹침·재개·주기·재시도·실패 알림 설정 | 파일 수동 전달 없이 반복되며 실패 구간을 성공으로 넘기지 않음 |

API를 연결했다는 것, DB 적재 성공, ES 검색 가능, 정기 자동화 완료를 각각 구분해 기록한다. W5까지 최소 연결 확인 전 대규모 검색 품질/부하 시험을 진행하지 않는다. 정기 수집을 평가와 함께 돌릴 경우 평가 스냅샷은 별도 고정한다.

목표 흐름은 [고용24 파이프라인](../app/ingestion/GOYONG24_PIPELINE.md)을 따른다. 현 DB가 EC2 루프백이므로 Lambda에서 직접 공개 DB로 붙는 것으로 변경하지 않는다. 공통 테이블은 재사용하되 현재 점핏 고정 SELECT·숫자 ID·후보/선택 API·캐시·근거의 출처 가정도 함께 수정해야 한다. 실제 필드 확인 없이 새 테이블/DDL을 확정하지 않는다.

## 4. 이후 검색 품질 시험

### 4.1 새 데이터에서 정답 다시 만들기

- 데이터 해시·기준 시각·출처/범위·노출 정책·필드·분석기·동의어·가중치·쿼리 규칙을 manifest로 고정한다.
- 기존80/60개는 적용 가능한 회귀 조건으로 재사용하되 건수·ID 정답은 고용24 스냅샷에서 다시 만든다. 기존975/747건의 점수·분모를 복사하지 않는다.
- 태그 제공 여부와 코드 품질에 따라 태그 검색/직종 코드 필터/본문 검색을 분리한다. API에 태그가 없는데 모델로 만든 태그를 원본 정답처럼 취급하지 않는다.
- 의료 등 비IT 분야도 포함하되 실제 승인 데이터의 직종 분포를 보고 구성한다. 단어 포함과 필수 면허·경력 충족을 구분하고 부정문·필수/우대·동음이의어·직종명 경계를 시험한다.
- 잠정 어휘 규칙 결과는 원문 증거 수집에 활용한다. 최종 관련성은 별도 사람이 원문과 검색 의도를 보고0~3점으로 판정한다. 모델 보조 판정은 독립 사람 라벨과 구분한다.
- SQL 정규화 대안은 미사용 표현과 다른 분야에서 검증한다. 튜닝/진단에 사용한60조건을 새 정확도 입증용 테스트셋으로 재포장하지 않는다.

### 4.2 공정한 비교군

1. 기존 DB 필터/문자열 SQL.
2. 수집 시 미리 만든 검색용 정규화 컬럼·적절한 색인을 사용하는 SQL 개선안.
3. MySQL FULLTEXT ngram 개선안.
4. 현 Nori ES.
5. 분석기·동의어·필드 가중치 중 한 요소만 바꾼 ES 후보.

항상 같은 출처·데이터·시간·필터·검색 대상 필드로 비교한다. 매 요청 본문 REGEXP_REPLACE를 실행하는 SQL만 대조해 'SQL이 느리다'고 결론내리지 않는다. 정규화·색인을 수집/갱신 때 준비한 SQL과 ES를 포함한다. 순위 가중치는 SQL에서도 표현 가능하므로 ES 전용 이점으로 간주하지 않는다.

### 4.3 보고할 지표

- 기능: 조건별 예상 건수·전체 ID, 누락/과잉, 기술명 경계·출처 분리·지역/직종/마감 필터 위반.
- 표현: 별칭·띄어쓰기·조사·복합어·다중 단어·직종 전환의 결과 일관성, 태그에 없는 본문 역량 회수.
- 관련성: 사람 라벨이 확보된 P@5/nDCG@5/MRR@5, 지정 대상 Hit@K. 전체 정답 없이 전역 Recall을 보고하지 않음.
- 오류 분석: '반환 후보 수 증가'와 '적합 공고 증가'를 구분. 추가 후보·무관 결과·필수조건 위반을 같이 제시.
- 의도 추출: Bedrock의 채용/교육/일반대화 및 AND/OR 판단은 별도 E2E 평가. 순수 검색 실험에는 모델 호출이 필요 없음.

자세한 정의와 분모는 [성능 평가 계획](PERFORMANCE_EVALUATION_PLAN.md)을 따른다. 위 기능 검증과 독립 사람 평가를 마치기 전 서비스 관련성 정확도 개선을 확정하지 않는다.

## 5. 규모·동시 사용자·비용 시험

고용24 데이터 파이프라인 연결 후 별도 단계로 수행한다. 실제 모델 없이 검색/DB 계층부터 시작해 모델 비용과 검색 비용을 분리한다.

- 데이터 규모: 실제 확보 데이터1배와 최소3배 규모. 단순 복제는 기술 부하용으로만 쓰고 직종 다양성·검색 품질 근거로 쓰지 않는다.
- 동시성: 1→5→10 등 작은 단계 제안. 실제 실행 전 테스트 시간·요청 상한·자원 여유·중단 조건을 정한다. 이 문서는 지금 유료 대규모 부하 실행을 승인한 기록이 아니다.
- 지연: p50/p95, 성공/실패율, 완료 처리량, 큐·DB·ES·정규화 구간. 워밍업·캐시·페이지 크기·반복수·실패 표본을 함께 기록한다.
- 자원: EC2 CPU/크레딧·메모리, MySQL/ES RSS, JVM 힙·GC·OOM·디스크·색인 크기·재시작.
- 갱신 비용: 수집 시 정규화·색인 시간과 검색 시 계산 시간 분리. 동기화 지연·Outbox 적체·갱신 중 검색 영향·재색인 복구 확인.
- 고정 조건: MySQL과 ES가 같은4GiB 호스트를 공유한다는 점을 보고한다. 한 번에 한 대조군 실행·기준 부하를 기록하고 자원 경합을 검색엔진 자체의 차이로 혼동하지 않는다.
- 장애: 실패·시간 초과·ES 장애 시 MySQL 복귀, 정상0건에서 불필요한 복귀 금지, 중복 저장·원문/근거 유실 없는지 확인.
- 비용: 테스트용 임시 자원·S3/SSM·고정 EC2 자원·인덱스 유지 비용을 기록한다. 모델 포함 실험은 별도 호출/토큰 한도 내에서 시행한다.

## 6. 보관 위치와 산출물

실험 실행 코드는 C:/AWS_project/검색평가_실험/<새 실행 ID>/code, 고정 입력·스냅샷·설정·정답·로그·결과는 같은 실행 폴더의 fixtures/data/results/graphs에 둔다. 서비스 실행 경로에서 import하거나 운영 설정을 바꾸지 않는다. 완료한 결과는 덮어쓰지 않는다.
