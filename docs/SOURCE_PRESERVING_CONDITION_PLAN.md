# 원문 보존 기반 조건 구조화·문답 QA 개선 계획

> 2026-11-02 1차 수정: [원문 보존 조건 분리 구현 기록](CONDITION_STRUCTURE_IMPLEMENTATION.md). `ㆍ` 분리·원문 위치/해시 검증·묶음 안내·구형 답변 승계 차단과 기존 JSON 근거 연결을 로컬 구현했다. 백엔드 256개 중 247개 통과·9개 제외, 프론트 23개 통과·빌드 성공. AWS 미배포이며 공통 정제 조건 저장/DDL·출력 제한 변경은 하지 않았다.

합의일: 2026-11-02. **설계·우선순위 기록이며 구현·DB 마이그레이션·운영 배포 완료를 뜻하지 않는다.** 이번 요청은 MD 수정과 문서 커밋·푸시만 수행한다.

## 1. 유지하는 구조와 보류 사항

- Elasticsearch: 제목·업무·자격요건·우대사항·기술 등 검색 사본에서 후보 검색·관련성 정렬.
- MySQL: 공고 원문·출처·버전·현재 상태와 사용자 문답·대화·근거의 기준 저장소.
- 정제/백엔드: 원문 보존, 조건 항목 경계 판별, 검증, 질문/답변 연결.
- Bedrock: 의도 해석·질문 표현·기록 기반 상담. 조건을 임의로 삭제하거나 자격 충족을 대신 판정하지 않는다.

검색엔진으로 문답 분리 문제를 옮기지 않는다. 검색 색인과 원문 DB의 역할은 유지한다. **출력 토큰 제한 변경은 사용자 요청에 따라 보류**한다. 실제 대화 QA에서 해당 실패를 계속 기록하되 자동으로 예산을 늘리거나 유료 재호출을 반복하지 않는다.

## 2. 현재 확인한 문제와 진단 한계

공고 55406955의 저장 버전 2에서 우대조건 원문은 24줄, `ㆍ` 문자는 8개였으나 현재 분리 결과는 2개 묶음이다. 분리 정규식이 `ㆍ`를 글머리표로 인식하지 못하는 것이 확인됐다. 글머리표 개수 자체가 반드시 정답 조건 수라는 뜻은 아니다.

‘이 중 몇 개는 해당되는 것 같다’는 보충 설명이 있어도 묶음 전체만 unknown으로 저장되어 개별 조건의 확인 상태를 알기 어렵다. 추가 기술스택 목록에 met를 선택한 것도 목록의 모든 기술을 개별 검증했다는 뜻이 아니다.

이력서·포트폴리오 후속 요청의 AWS 기록에는 ModelOutputFormatError, 입력 6,612/출력 1,024토큰이 남았다. 출력은 현재 상한에 도달했으므로 잘림 가능성이 높지만 종료 사유를 별도로 저장하지 않아 확정할 수 없다. 이 기록을 SQL 저장 용량 오류로 해석하지 않는다. 이번에는 출력 설정을 변경하지 않는다.

## 3. 원문 보존과 구조화 원칙

구조화는 **원문을 요약·재작성하는 작업이 아니라 항목 경계와 연결 정보를 붙이는 작업**이다.

1. 수집 원본과 MySQL에 저장한 섹션 문자열을 보존한다. 구조화 결과로 원본을 덮어쓰지 않는다.
2. `ㆍ`, `•`, `-`, 번호 등 명확한 목록 경계를 인식하되 괄호·들여쓰기·이어지는 설명을 함께 고려한다.
3. ‘Python 또는 Java’, ‘경력 3년 이상 또는 이에 준하는 역량’ 같은 대안은 독립 필수 조건으로 쪼개지 않는다. AND/OR·숫자·단위·부정·예외·괄호 문구를 보존한다.
4. 애매한 경계는 임의로 확정하지 않고 묶음/분리 검토 대상으로 남긴다. 인접 문장의 의미 관계를 글머리표 하나만으로 추정하지 않는다.
5. 화면의 짧은 표시는 원문과 구분한다. 사용자에게 조건 전체 원문과 공고 출처·당시 버전을 확인할 수 있게 한다. 축약 문구를 새로운 판정 근거로 사용하지 않는다.
6. 자동 분리 검증 실패 시 조용히 일부 조건을 버리지 않는다. 검토 상태를 기록하고 기존 원문 묶음으로 표시하거나 질문 생성을 보류한다.

## 4. 공통 기준 데이터·사용자 기록·캐시 구분

| 구분 | 보관 내용 | 목적 |
|---|---|---|
| 공통 공고 조건 | 공고 원문과 연결된 검증된 구조화 항목 | 여러 사용자가 같은 공고 버전의 조건을 반복 파싱하지 않도록 함 |
| 사용자 노출·답변 | 실제 보여준 조건 세트·항목·버전·당시 원문, 선택값과 보충 설명 | 무엇을 보고 어떻게 답했는지 재현하는 근거 |
| 캐시 | 동일 요청의 임시 처리 결과와 버전 참조 | 반복 계산·중복 처리 감소 |

사용자에게 보여준 구조를 보관하는 것도 필요하지만 공통 구조화 조건은 사용자 접속 전에 정제 단계에서 생성하는 기준 데이터다. 둘을 캐시 하나로 대체하지 않는다. 캐시가 만료돼도 유효한 문답 근거를 잃지 않도록 기존 세션 보관 정책과 분리한다. 세션 조회 만료와 물리 삭제·백업 보존은 별도 과제다.

## 5. 저장 계약 초안 — DDL 미확정

공통 조건 세트에는 다음 정보를 연결하는 방향으로 설계한다.

- `source + source_id`, 공고 `source_version`, 섹션 종류(qualifications/preferred_requirements).
- 비교 기준인 저장 섹션 원문 스냅샷과 UTF-8 해시, 분리 규칙 버전, 조건 세트 버전/식별자, 검증 상태.
- 항목별 안정된 ID, 순서, 필수/우대 구분, 원문 발췌, 경계 확신/분리 보류 상태.
- 원문 위치는 기준 문자열을 명시한 문자 오프셋(시작 포함·끝 제외 등)으로 정의한다. 바이트 위치·화면 위치·다른 정규화 문자열의 인덱스를 섞지 않는다.
- 항목은 원문 연속 구간과 연결한다. 제목+본문처럼 비연속 구간을 함께 표시해야 하면 구간 목록과 결합 방식을 기록한다. 문자·줄바꿈을 임의로 지운 뒤 원문과 같다고 판정하지 않는다.

JSON 컬럼 활용과 별도 조건 세트/항목 테이블을 비교한 뒤 저장량·조회·제약·갱신/복구 기준으로 확정한다. 이번에 새 테이블 생성이나 기존 데이터 재작성을 하지 않는다.

사용자 노출·답변은 조건 세트 ID, 항목 ID, 공고/정제 버전, 당시 원문/해시 참조, 응답 선택·보충 설명과 요청/메시지 참조를 연결한다. 기존 chat_sessions·chat_messages·recommendation_evidence 재사용 범위를 먼저 확인한다.

## 6. 검증과 버전 변경

- 모든 항목의 원문 구간이 실제 섹션과 일치하는지 검사한다. 서로 다른 공고·버전·섹션의 참조를 차단한다.
- 누락·중복·의도치 않은 겹침·순서 뒤바뀜을 검사한다. 비질문 제목·공백·목록 구분자도 분류해 설명되지 않은 원문 누락을 감지한다.
- 숫자/단위/부정·대안·예외 변경을 별도로 QA한다. 문자열 일치만으로 잘못된 경계 분리까지 안전하다고 판단하지 않는다.
- 원문이 바뀌면 새 공고 버전과 연결된 조건 세트를 만든다. 분리 규칙만 바뀌면 원문을 수정하지 않고 새 정제 버전을 만든다.
- 과거 세트와 당시 사용자 답변은 유지한다. 새 항목에 이전 met/unmet/unknown을 자동 복사하지 않는다. 특히 묶음 ‘일부 해당’을 개별 충족으로 배분하지 않는다.
- 신·구 버전 혼재 세션, 재시도 중복·부분 저장 실패·롤백과 캐시 버전 분리를 검증한 뒤 운영 반영한다.

## 7. 단계별 구현 순서

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 현재 분리 함수의 `ㆍ` 인식과 원문 보존 회귀 검사 | 알려진 실패 사례 개선, 기존 OR/괄호/하위 설명 보존, 잘못된 전역 분리 없음 |
| 2 | 정제 파이프라인에서 경계·발췌·검증 결과 생성 | 누락/중복/원문 변경 탐지, 애매한 항목 검토 상태·보수적 복귀 |
| 3 | 공통 구조화 조건 저장·읽기 계약 확정 | 최소 DDL/JSON 선택, 버전·출처·ID·복구 설계 후 격리 저장 시험 |
| 4 | 화면 노출과 사용자 답변 연결 | 실제 보여준 조건을 재현, 기존 묶음 답변 자동 승계 금지 |
| 5 | 보충 설명·문답 요약·후속 상담 QA | 선택과 설명 충돌 시 둘 다 보존, unknown을 unmet으로 바꾸지 않음, 질문 거절 유지 |
| 6 | 학습 루트 고도화 | 관련 교육 조회를 넘어 부족 기술→선수지식→기초→실습→프로젝트와 교육 근거 연결 |

고용24 연동 준비와 병행할 수 있는 현재 분리 오류·QA부터 진행한다. 공급원 확대와 전 직군 검증, 구조화 조건의 운영 일괄 생성은 별도 단계로 검증한다. 경력·학위·면허를 교육으로 대체하거나 학습 루트로 합격을 보장하지 않는다.

## 8. 대화 QA 기록과 필수 사례

사례별로 **입력/상태 → 기대 동작 → 실제 결과 → 오류 분류 → 재현 횟수 → 수정 버전 → 재검증 결과**를 남긴다. 한 번 성공한 것을 안정성 확보로 표현하지 않는다. 선택/보충 설명 해석, 처리 오류, 원문 분리 문제를 구분한다.

- `ㆍ`/번호/여러 줄 목록, 괄호·하위 설명·OR/AND·부정·예외·경력/학력 수치.
- 일부 충족·일부 미확인, 선택과 보충 설명 충돌, 질문 중단 요청, 문답 후 부족 역량 정리.
- 전부 충족한 경우의 이력서/면접 안내와 미확인 항목 설명. 과거 경험을 근거 없이 다시 묻거나 성과 수치를 만들지 않음.
- 채용→교육 전환, 교육 비교, ‘왜 추천했어?’의 사용자 발언·공고 근거 참조.
- 원문/정제 버전 변경 전후 답변, 오래된 화면·캐시·중복 요청, 만료/다른 소유자 접근.
- 후속 상담 형식 실패와 동일 대화 재시도. 기존 답변 손실 여부를 확인하고 출력 제한 변경은 보류로 표시.

이번 문서에 새 회귀 테스트가 통과했다고 기록하지 않는다. 실제 QA 원문·세션 식별 자료는 기존 비공개/접근 통제 경로에 보관하며 Git 문서에는 비밀정보·개인 대화 원문을 넣지 않는다.
