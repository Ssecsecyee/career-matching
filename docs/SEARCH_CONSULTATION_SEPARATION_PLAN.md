# 검색·후속 상담 경로 분리 개선 계획

합의일: 2026-11-02. 상태: **방향 기록 / 미구현·미배포**. 이번 요청은 MD 작성과 관련 계획 연결만 수행한다. 기존 출력 예산 확대 배포와 이 분리 계획의 구현 여부를 구분한다.

## 1. 확인된 현상과 원인 구분

문답 요약의 ‘이력서에 연결’, ‘보완 방향 정리’ 버튼도 현재 일반 입력과 같은 action=search 진입점을 사용한다. 서버가 BedrockPlanner.route로 검색/상담을 다시 분류하도록 요청하고, 모델이 생성한 JSON 객체를 검사한다.

실제 QA에서는 route 출력 상한을 1,024에서 4,096토큰으로 늘린 뒤 이력서 상담이 정상화됐지만, 보완 상담은 출력 1,136토큰에서도 형식 오류가 발생했다. 추가 진단은 출력 1,758토큰·end_turn으로 종료됐는데 허용 JSON 객체로 파싱되지 않았다. 상한 도달과 JSON 형식 준수는 서로 다른 문제다.

오류가 났다는 사실만으로 모델이 search 의도를 선택했거나 Elasticsearch를 실행했다고 해석하지 않는다. 확인된 실패는 route가 유효한 분류 결과를 반환하기 전 형식 검사에서 발생한 것이며, 해당 경로에서는 이후 jobs.search까지 도달하지 않는다. 원시 응답을 보관하지 않아 구체적인 문장·펜스 형태까지 확정하지 않는다.

핵심 설계 문제는 이미 목적이 정해진 상담 버튼을 검색/상담 재분류와 모델 생성 JSON 계약에 의존시킨 것이다. 검색을 해야 할 때만 검색 계획을 만들고, 상담은 저장된 공고·사용자 답변을 이용하는 별도 경로로 처리한다.

## 2. 목표 흐름

```text
공고/교육 검색 요청
 → 검색 대상·조건 검증 → 검색 실행 → 최신성 확인 → 검색 설명/확인·후보 표시

요약 후 상담 버튼
 → 상담 전용 요청 검증 → 같은 소유자의 저장 문답/원문 조회
 → 상담용 Bedrock 자연어 응답 → 서버가 JSON 응답으로 포장·저장

다른 공고 찾기
 → 검색 경로

나중에 확인/단순 저장된 요약 조회
 → 가능한 범위는 서버의 기존 기록으로 처리, 불필요한 모델 호출 생략
```

API Gateway 주소나 HTTP 엔드포인트를 새로 만들 필요는 없다. 기존 POST /api/chat 안에서 논리 action과 서버 처리 경로를 분리한다. 일반 사용자/관리자 토큰·세션 소유권·호출 기록·응답 캐시 정책은 유지한다.

## 3. 상담 전용 요청 계약 초안

```json
{
  "action": "consult",
  "task": "prepare",
  "session_id": "현재 세션 UUID",
  "request_id": "새 요청 UUID",
  "summary_id": "버튼이 참조한 답변 요약 ID",
  "message": "이미 답변한 경험을 이 공고의 이력서와 포트폴리오 준비에 연결해줘."
}
```

위 형식은 제안이며 현재 운영 API에서 허용되는 요청이 아니다. task는 서버 허용 목록으로 검증하며 임의 SQL·DSL·추가 권한 지시로 사용하지 않는다. message 길이·UUID·세션·선택 공고·참조 요약 버전을 검증한다. 오래된 버튼의 summary_id가 현재 상태와 다르면 임의로 새 요약에 적용하지 않고 갱신/재확인을 안내한다.

## 4. 현재 버튼별 처리

| 기존 action ID | 의미 | 개선 후 처리 |
|---|---|---|
| prepare | 이력서·포트폴리오 연결 | consult, 저장한 경험·자기평가로 문장 예시와 증빙 준비 안내 |
| interview | 면접 준비 | consult, 해당 공고·답변을 바탕으로 준비 방향 제안 |
| learning_plan | 미충족 조건의 보완 방향 | consult, 부족 기술·미확인·우대와 경력/학위 구분. 교육 검색을 자동 실행하지 않음 |
| explain_unknown | 미확인 조건 설명 | consult, 당시 원문을 설명하고 미확인을 미충족으로 바꾸지 않음 |
| defer | 나중에 확인 | 서버에서 상태/요약 안내 우선. 동의 없이 문답 재개나 새 조회 금지 |
| similar_jobs | 다른 공고 찾기 | search, 기존 검색 설명/확인 흐름 활용 |

버튼의 action ID를 프론트에서 전달하고 서버도 의미를 검증한다. 버튼 문장 안의 ‘공고’·‘교육’ 단어만으로 검색에 보내지 않는다. 상담 경로에 search_plan이 들어오면 허용하지 않는다.

자유 입력도 명시적 후속 상담이면 선택 대상과 저장 상태에 근거해 상담 경로로 연결한다. 다만 ‘이력서에 React 경험이 있는데 관련 공고를 찾아줘’처럼 실제 검색을 요청한 문장은 상담 단어만으로 가로채지 않는다. 여러 의도가 섞이거나 대상이 모호하면 짧게 확인하고 두 경로를 임의로 동시에 실행하지 않는다.

## 5. 상담용 모델 어댑터와 응답 계약

- 상담 전용 어댑터는 자연어 답변을 요청한다. 모델이 다시 intent/chat/plan JSON을 생성하거나 검색 도구를 선택할 필요가 없다.
- 서버는 생성된 텍스트를 검증한 뒤 기존 stage=conversation, message 등의 JSON 응답으로 직렬화한다. 모델 생성 JSON과 HTTP 응답 JSON은 다른 계층이다.
- 자연어 허용은 상담 전용 경로에 한정한다. 검색 계획 JSON·Pydantic 검증과 임의 SQL/DSL 금지는 그대로 유지한다. 일반 검색에서 JSON 검사가 실패했다고 아무 텍스트나 검색 계획으로 받아들이지 않는다.
- 현재 QA 예산 4,096토큰과 reply 4,000자, 원시 스트림/시간 보호의 정합성을 유지한다. 빈 응답·지원하지 않는 콘텐츠·잘림·연결 중단은 정상 완료로 저장하지 않는다. 무제한 출력·자동 반복 호출은 도입하지 않는다.
- max_tokens와 정상 end_turn 후 계약 오류, 스트림 장애를 구분해 사용량·안전한 진단 코드로 기록한다. 원문 모델 응답·인증값·개인 대화를 운영 로그에 덤프하지 않는다.

## 6. 문맥·근거와 학습 조회 정책

상담에는 같은 소유자·유효 세션의 사용자 원문/보충 설명, 조건별 선택, 당시 공고/조건 버전, 원문 발췌, 요약·묶음 안내를 필요한 만큼 전달한다. 미확인/미답변을 미충족으로 바꾸거나 기술목록 묶음 met를 개별 기술 검증으로 확대하지 않는다.

기존 원문과 당시 문답을 활용하는 상담에 Elasticsearch 검색을 필수로 붙이지 않는다. 과거 공고 버전으로 상담할 때는 당시 조건 기준임을 명시하고 현재 모집 상태를 확인했다고 말하지 않는다. 사용자 경력·성과 수치를 만들거나 학위/경력을 교육 수료로 대체하지 않는다. 역량 질문 중단 설정도 유지한다.

‘교육 수료로 대체하지 마’라는 제한 문구는 교육 검색 요청이 아니다. 일반 보완 상담에서 미충족 항목이 있다는 이유만으로 교육 조회/need_topic 카드를 자동 붙이지 않도록 분리한다. 이미 표시한 교육이 있으면 그 범위의 사실을 참고할 수 있지만 새 과정·일정·모집 여부를 만들지 않는다. 사용자가 실제 과정을 찾아달라고 요청했을 때 기존 교육 검색 경로로 명시적으로 전환한다.

‘왜 추천했어?’는 별도 근거 조회 의도다. 검색 당시 기록을 먼저 읽어야 하며 상세 일치 근거 writer/과거 조회가 아직 미완성인 범위를 일반 상담 분리 완료와 혼동하지 않는다.

## 7. 스트리밍·저장·호환

- 상담 텍스트 스트림은 JSON reply 문자열 추출기가 아닌 명시적인 텍스트 모드로 전달한다. 모드는 서버의 검증된 상담 경로가 선택하며 검색 JSON이 초안으로 노출되지 않도록 한다.
- 질문 거절 등 최종 필터를 거치기 전에 문제가 되는 초안이 노출될 수 있는 경로는 스트리밍을 제한하거나 같은 정책을 적용한다.
- 정상 완료 응답과 대화/사용량/참조는 기존 트랜잭션 저장·소유자 격리·만료·요청 ID 중복 방지 안에서 처리한다. draft와 최종 저장 답변을 구분한다.
- 실패 시 기존 문답을 유지하고 같은 대화에서 재시도할 수 있게 한다. 단순 형식 오류만으로 새 대화를 강요하지 않는다.
- 기존 웹은 당분간 action=search로 상담 버튼 문장을 보낼 수 있다. 알려진 후속 버튼/상태의 제한된 호환 처리로 상담에 연결하고, 모든 search 요청을 상담으로 돌리지 않는다.
- 권장 반영 순서는 구형 요청 호환을 가진 백엔드 → 새 버튼 요청을 보내는 웹 → 소량 실제 검증이다. 복귀 시 새 action을 모르는 구형 백엔드와 새 웹이 남지 않도록 웹/API 버전을 함께 관리한다.

## 8. 구현 순서

1. consult/task/summary 참조 검증과 버튼별 서버 분기, 검색 미호출 조건을 고정한다.
2. 기존 검색 전처리보다 앞에서 상담을 분리하고 저장 문맥을 구성한다. 선택 대상이 없거나 만료된 경우 안전하게 안내한다.
3. 상담 전용 텍스트 모델 어댑터와 스트리밍 모드를 구현한다. 기존 검색용 JSON 어댑터는 유지한다.
4. 프론트 요약 버튼의 ID별 요청과 구형 웹 호환을 연결한다. 다른 공고 찾기는 검색 경로로 유지한다.
5. 모의 모델/저장소 회귀 검사 후 승인된 소량 실제 QA와 AWS 반영을 진행한다. 이번 문서 작성은 이 작업의 실행 승인이거나 완료 증거가 아니다.

## 9. 완료 기준과 QA

| 사례 | 기대 동작 |
|---|---|
| 이력서·포트폴리오 연결 | 상담 호출 1회, ES/새 교육 검색 0회, 자연어 응답 정상 저장 |
| 미충족 기준 보완 방향 + 교육 수료 대체 금지 | 상담으로 유지, 경력/학위 대체 금지, 불필요한 need_topic 카드 없음 |
| 미확인 설명·역량 질문 거절 | 원문/기존 답변 활용, 새 체크리스트 자동 시작 없음 |
| 다른 공고 찾기 | 검색 계획 검증·검색 설명/확인·후보 표시 흐름 유지 |
| 명시적 교육 검색과 단순 교육 언급 | 실제 요청만 교육 조회로 전환, 상담은 과정 정보 조작 없음 |
| 자유 입력 복합 의도 | 명시적 검색을 단순 이력서 단어로 가로채지 않으며 애매하면 확인 |
| 정상 end_turn 텍스트·긴 응답 | 상담에 불필요한 모델 JSON 강제 없음, 길이 보호와 스트리밍 정상 |
| 잘못된 검색 JSON·중단 스트림·max_tokens | 검색 검증 유지, 실패 구분·기존 답변 보존·자동 유료 재호출 없음 |
| 오래된 버튼·중복·다른 소유자·만료 | 잘못된 상태 적용 차단, 중복 모델/답변 저장 방지 |
| 구형 웹/진행 중 세션 | 호환 동작, 기존 원문/답변과 질문 거절 상태 유지 |

실제 QA에서는 두 실패 버튼을 같은 문답 상태에서 재검증하고 요청 목적·선택 공고 버전·검색 호출 횟수·모델 호출 횟수·종료 사유·토큰·지연·저장 결과를 기록한다. 정상 end_turn이나 HTTP 200만으로 답변 내용의 사실 정확성까지 통과했다고 판단하지 않는다.
