# 선택 공고 SQL 질문 캐시 AWS 배포

일자: 2026-11-03 / 상태: 배포·활성화·무모델 호출 검증 완료

## 배포 범위

기존 EC2의 MySQL에 job_condition_question_cache를 추가하고 런타임 SELECT/INSERT 권한을 부여했다. 원본·승인 분류·기존 사용자 답변은 수정하지 않았다. QA용 새 세션과 답변만 생성했다. 별도 서버·DB 인스턴스·공개 포트는 만들지 않았다.

준비 도구는 infra/on_demand_conditions.py, 원격 설치기는 infra/install_on_demand_conditions.py다. 백업·테이블/권한 준비와 코드 배포 후 활성화를 분리했다. 기존 update_backend.py로 백엔드 20261103T020923Z를 반영했고 배포된 주요 파일의 해시를 대조한 뒤 ENABLE_ON_DEMAND_CONDITIONS=true를 설정했다. 코드 교체/활성화 시에 작업자를 재시작했다. 웹 파일 변경이 없어 CloudFront 배포 설정은 변경하지 않았다.

## 확인 결과

- 기존 MySQL 전체 압축 백업의 읽기·SHA-256 검증 통과. 같은 서버 백업이며 서버 밖 복구 대책을 대체하지 않는다.
- 채용 1020건·교육 7건의 ID/버전/내용 해시 유지.
- 런타임 조회·추가 권한과 실제 두 DB 연결의 중복 이름 잠금 차단 확인.
- 기존 검토 공고 55406955를 서로 다른 사용자 2명이 선택했을 때 같은 필수 질문 2개와 참고조건 2개를 받았다.
- 첫 사용자의 미확인 답변을 저장한 뒤, 두 번째 사용자의 답변 수는 0이고 조건 상태는 미답변으로 유지됐다.
- 검증 세션 2개의 model_call_count와 model_invocations는 모두 0. 새 Bedrock 호출 없이 승인 결과를 재사용했다.
- 작업자·검색 동기화 타이머 정상, 선택 시 처리 플래그 활성화 확인.

## 검증 한계와 운영 경계

배포 검증은 기존 승인 분류를 사용했다. 질문 전용 캐시 테이블의 운영 행은 종료 시 0건이다. 새 캐시의 실제 저장·공유·권한·동시성은 로컬 격리 MySQL에서 검증했다. 운영에서 새로운 공고를 실모델로 처음 생성하는 정확도·지연·비용 시험은 이번에 하지 않았다.

신규 공고를 선택하고 승인 결과/질문 캐시가 없으면 제한된 질문 라벨 호출이 발생할 수 있다. 전체 공고 일괄 추출은 여전히 보류이며 자동 대량 처리 스케줄을 만들지 않았다. 캐시 저장은 Outbox/ES 이벤트를 만들지 않는다. 실패 시 원문 문답으로 복귀한다. 의미 정확도를 독립적으로 검증한 것으로 해석하지 않는다.

## 복귀

ENABLE_ON_DEMAND_CONDITIONS=false로 되돌리고 작업자를 재시작하면 기존 문답 경로로 돌아간다. 캐시 테이블·원문·답변을 삭제하지 않는다. 설치기는 활성화 실패 시 이전 보호 설정을 복원하도록 준비했다. 비밀 설정·DB 비밀번호·접속 토큰은 문서와 Git에 포함하지 않는다.
