고정 revision과 체크섬으로 모델을 확인했다. 기존 worker 환경에 모델 패키지를 설치하지 않았다. 구축 중 관측한 프로세스 메모리는 약 778MiB였고, 예시 검색 검증의 최대 RSS는 881.5MiB였다. 이는 동시 사용자 부하 시험 결과가 아니다. CPU는 단일 코어의 50%로 제한했다. 기존 EC2 비용과 CPU·네트워크 사용은 별도로 존재한다.

## 검색 동작 확인

개인정보 없는 가상 경험 5개를 같은 모델로 임베딩하고, 자격요건·우대요건을 각각 검색한 뒤 공고 단위로 합쳤다. 두 섹션의 최대 코사인 값을 사용하는 초기 기준이다. 점수는 자격 충족률이 아니다.

| 가상 경험 | 상위 검색 사례 | 관찰 |
|---|---|---|
| Python/Django/PostgreSQL/Docker/AWS | 풀스택 제품 개발자, 보안 연구소 솔루션 개발자 | 백엔드 외 직무도 포함 |
| React/TypeScript/HTML/CSS | 프론트 엔지니어, Frontend 개발자 | 관련 직무 확인 |
| Python/PyTorch/TensorFlow | 머신러닝 엔지니어, AI 개발자 | 관련 직무 확인 |
| C/C++/Linux/MCU | 임베디드 개발자, 메카트로닉스 엔지니어 | 관련 직무 확인 |
| MySQL/PostgreSQL/SQL 최적화 | 백엔드 개발자, Windows Application 개발자, DBA | 일부 약한 관련성, 순위 개선 평가 필요 |

모델을 한 번 로드한 상태의 짧은 예시 5건 검색은 건당 0.137~0.379초였다. 전체 검증은 4.97초였다. 긴 실제 자소서, 콜드 스타트, 다중 사용자 지연을 대표하지 않는다. 정답 라벨 평가를 하지 않았으므로 정확도 수치는 산출하지 않았다.

## 원문 및 개인정보 경계

- 원문 두 섹션은 문장 분리·요약 없이 보존했다.
- `(source, 문자열 source_id)`와 버전·섹션 해시·모델 지문을 저장했다.
- 검색 후보를 현재 운영 ES 사본과 재대조해 변경·삭제된 후보를 제외한다. MySQL 기준 재검증 연결은 화면 통합 전 남은 작업이다.
- 가상 자소서 임시 파일은 검증 후 삭제했으며, 공고 색인·공용 캐시에 자소서를 저장하지 않았다.
- 기존 worker는 구축 중 정상 상태였다. 신규 AWS 리소스를 생성하지 않았다.
