# 기존 문맥 라우터와 AgentCore Harness 비교 실험

상태: 제안 · 평가셋/실행기 미구현 · 실제 모델 미실행
기준일: 2026-11-06

## 비교 질문

같은 업무 도구·데이터·검증 정책에서 Harness가 기존 ContextRouter보다 문맥에 맞는 기능 선택과 근거 답변을 개선하는가? 새 도구 래핑으로 인한 개선과 Harness 자체 효과를 구분한다. 토큰·서비스 비용·지연·운영 복잡도까지 함께 비교한다.

A: 현재 배포된 ContextRouter + Bedrock Sonnet + 서버 검증.
B: AgentCore Harness + 같은 기본 모델(연결 가능성 확인 후 고정) + 같은 서버 검증/업무 도구.

기존 분류 전용 정확도 평가와 달리 B는 별도 intent JSON을 항상 생성하지 않을 수 있다. 두 방식은 허용 업무 행동·도구 실행·최종 결과로 비교한다. 같은 의미의 복수 실행 순서는 허용한다.

## 데이터와 정답 고정

초기 50개는 다중 턴을 포함한 시나리오 단위다. 총 사용자 턴·모델 호출 수는 별도로 집계한다. 개발용 smoke 5개는 50개와 분리한다. 기존 정식 120건 의도 평가 계획은 유지하며 이번 50개를 그 평가 완료로 보고하지 않는다.

| 그룹 | 시나리오 수 |
|---|---:|
| 신규 채용 검색·복합 조건·검색 기준 확인 | 8 |
| 채용/교육 전환·교육 비교 | 8 |
| 다음 결과·중복 제외·교육 다음 목록 | 8 |
| 저장 답변 요약·추천 근거·조건 버전 | 8 |
| 질문 중단/재개·모름·명시 답변 수정 | 6 |
| 충족 경험 기반 유사 공고·필수조건 보존 | 6 |
| 대상 모호·일반 대화·도구 장애·중복 요청 | 6 |
| 합계 | 50 |

각 사례에는 case_id, 합성 이전 대화/초기 상태, 사용자 입력 순서, 허용 업무 행동/도구, 금지 실행, 유지할 제약, 조회 가능한 근거, 필요한 최종 답변 사실, 정답 공고 집합이 필요한 경우 고정 스냅샷 근거를 둔다. 문장 표현이나 모델의 설명문 전체를 정답 문자열로 강제하지 않는다.

사용자 승인 전 카드 공개 금지, 질문 중단, 다른 사용자의 세션 조회 시도, 원문/버전 변경, 검색0건, 검색엔진 장애, 저장실패/부분실행, 재전송을 포함한다. 오타·줄임말·같은 '딴거'의 채용/교육/대상없음 문맥을 포함한다. 세부 배분은 작성 시 중복 태그로 보완한다.

두 평가자가 가능하면 독립 라벨링하고 불일치는 합의 또는 모호 사례로 분리한다. 평가용 사례를 프롬프트 튜닝에 사용하면 개발셋으로 전환하고 별도 보류셋을 마련한다. 아직 라벨링/평가셋 생성이 완료됐다고 표현하지 않는다.

## 고정 조건과 실행 통제

- 모델/추론 프로필, 가능한 생성 설정, 프롬프트·도구·검색 정책·코드 버전, DB/ES 스냅샷 해시를 기록한다. 플랫폼 내부 지침/호출 구조까지 같다고 주장하지 않는다.
- 실사용자 개인정보 대신 합성 문맥/계정/ID를 사용한다. 읽기 전용 기능을 우선하고 수정 도구 검증은 격리 DB에서 수행한다.
- 동일 초기 상태에서 각 엔진을 새 세션으로 시작한다. 기존 경로 결과가 Harness의 문맥·캐시를 오염시키지 않게 한다.
- 실행 순서를 교차/무작위화하고 캐시·cold/warm·재시도·시간대 영향을 기록한다. 데이터가 바뀌면 동일 실험 버전으로 비교하지 않는다.
- 최초 smoke 후 50개 단일 실행으로 오류를 찾는다. 불확실성을 확인할 반복 실행은 별도 비용 승인 범위에서 진행하고 첫 실행/반복 결과를 분리한다.
- 초기 제한 제안은 사용자 턴당 업무 도구 실행 최대 3회, 모델/플랫폼 반복과 전체 벽시계 제한을 명시하는 것이다. 정확한 API 설정값과 서버 강제 상한은 smoke 전 검증한다. 도구 수와 모델 호출 수를 같은 것으로 집계하지 않는다.
- 비용 상한은 아직 미정이다. 상한 확정 전 리소스 생성·유료 평가를 진행하지 않는다. 모델 추론 + Harness 실행 + 선택 부가 서비스 + 로그/저장/데이터 전송을 합산한다.
- 자동 유료 재시도를 평가기에 기본 탑재하지 않는다. 부분 실행 후 재시도는 동일 도구 호출의 멱등성/진행 기록 확인 후 수행한다.

## 지표와 제안 전환 관문

| 지표 | 계산/판정 | 제안 관문 |
|---|---|---|
| 업무 행동 적합도 | 턴별 허용 행동을 수행한 수 / 평가 대상 턴 | A 이상, 추가로 시나리오 완주율 비교 |
| 시나리오 완주율 | 요구·금지 조건을 모두 충족한 시나리오 / 전체 | A 이상, 실패 건수·분모 함께 제시 |
| 불필요한 도구 실행률 | 정답상 불필요한 도구 호출 / 전체 도구 호출 | A 대비 악화하지 않을 것 |
| 조건 보존 | 사용자가 해제하지 않은 명시 제약 유지 | 100% |
| 다음 목록 중복 | 이전 노출과 겹친 ID | 0건 |
| 중단 의사 준수 | 중단 후 승인 없는 역량 질문 | 0건 |
| 근거 정합성 | 선택·문답·추천 버전과 최종 인용 사실 일치 | 사례별 체크, A 이상 |
| 도구 계약/응답 실패 | 파싱·스키마·실행 오류/대상 호출 | 건수와 실패 유형 공개, A 이상 |
| 기록 완전성 | 요청→도구→결과/실패→근거 연결 | 100% |
| 사용자별 접근 경계 | 다른 사용자의 데이터 조회·수정 | 0건, 발생 시 전환 차단 |
| 승인 없는 변경·허위 합격 판정 | 저장 답변 변경·현재 모집/합격 사실 조작 | 0건, 발생 시 전환 차단 |
| 지연 | 전체 사용자 응답 p50/p95, 최초 표시 지연, 큐/모델/도구/저장 분해 | A 실측 후 허용 범위 합의 |
| 사용량·비용 | 사용자 요청/완주 시나리오당 총량, 실패 포함 | A 실측과 예산 후 허용 범위 합의 |

제안 관문은 합의/측정 전이며 달성 결과가 아니다. 작은 표본에서 백분율만 제시하지 않고 오류 건수·분모·불확실성을 같이 보고한다. 5개 smoke로 정확도나 p95를 발표하지 않는다. 모델이 도구 요청을 만들었지만 서버가 차단했다면 '모델 오요청'과 '실제 위험 실행 차단'을 따로 집계한다.

## 필수 사례 예시

| 문맥/발화 | 기대 행동 | 금지/주의 |
|---|---|---|
| 채용 목록 이후 '딴거' | 이전 검색의 다음 결과 | 새 기준 재생성·기존 카드 반복 |
| 교육 목록 이후 '이중 제일 추천?' | 표시 교육·사용자 경험 근거로 비교 | 채용공고 비교로 오해·미조회 교육 생성 |
| '내가 미충족이라고 한 내용 정리해줘' | 저장 답변 조회·원문 연결 요약 | 새 채용 검색·unknown을 unmet으로 처리 |
| '질문하지 말고 찾아줘' | 중단 선호 반영·가능한 검색 | 조건 문답 반복 |
| '필수 4개 충족했어, 유사한 다른 공고는?' | 저장 답변 조회·관련 후보 검색 | 원 공고 필수조건을 전부 강제필터로 복사 |
| '왜 이걸 추천했어?' | 해당 검색·후보·문답 근거 조회·설명 | 뒤늦게 이유 창작·다른 공고 근거 사용 |
| '부산만, Python 반드시' 이후 다른 요청 | 지역·명시 필수 유지 | 후보 늘리려고 몰래 완화 |
| 검색엔진 장애 / 검색 0건 | 기존 장애 정책 적용 / 0건 사실 안내 | 정상 0건을 장애로 간주해 우회 |
| 버튼 확인·조건 답변 | 기존 직접 API | 불필요한 의도 분류 호출 |

## 보고 산출물

공개 가능한 합성 시나리오/평가 계약/집계 코드와 비공개 실제 결과·추적을 분리한다. 보고서에는 설정·데이터 버전, 시나리오/턴/호출 분모, 업무 행동 혼동, 오류 유형, 근거 오류, 불필요한 도구, 지연, 비용, 미측정 항목, 실패 사례와 결정을 담는다. 관리자에서는 run_id/request_id로 같은 기록을 조회한다.

결론은 유지/추가 개선/제한 전환/전환 보류 중 하나다. 품질 개선 없이 코드가 줄었다는 이유만으로 운영 전환하지 않는다. 기존 분류 모의 테스트 통과와 실제 모델 정확도를 구분한다.

연결: [전환 계획](AGENTCORE_HARNESS_ADOPTION.md), [기존 문맥 평가](../CONTEXT_INTENT_EVALUATION.md), [전체 성능 평가](../PERFORMANCE_EVALUATION_PLAN.md).

## 메모리 역할 분리 검증

목표 설계는 [도입 계획의 세션과 기록 설계](AGENTCORE_HARNESS_ADOPTION.md#세션과-기록-설계-초안)를 따른다. AgentCore 문맥과 MySQL 확정 기록을 분리하고 다음을 평가한다.

- 대화 요약에 일부 항목이 없어도 DB 도구로 전체 확정 답변과 보충 설명을 정확히 조회하는가.
- unknown·미답변과 unmet을 구분하고 경력 부족을 교육 수료로 대체하지 않는가.
- 사용자 답변 수정 후 오래된 Memory보다 최신 DB 답변 버전을 우선하는가.
- 원문 버전이 바뀌면 과거 답변을 현재 공고의 충족 판정으로 재사용하지 않는가.
- 다른 사용자/세션의 Memory·답변·추천 근거를 섞지 않는가.
- 답변 저장 실패 시 저장 성공을 주장하지 않으며, 같은 요청 재시도 시 중복 기록을 만들지 않는가.
- 스크롤·문답 버튼·상세 조회는 에이전트 모델 호출 없이 실행되는가.
- 대화 만료·삭제 시 합의된 보존 정책에 따라 DB와 Memory를 각각 처리하는가.

이번 문서 수정은 설계 기록이다. AgentCore·Memory 연결, DB 스키마 변경, 유료 평가 또는 운영 전환이 완료됐다는 의미는 아니다.
