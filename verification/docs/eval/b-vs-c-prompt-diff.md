# 기존 프롬프트(B)와 내 규칙(C)의 차이 — V3·V4 기술 추출 실험

## 0. 구성
| | 시스템 프롬프트 | 파일 |
|---|---|---|
| **B (기존)** | 친구의 분류기 설명서만 사용 | `career-matching/app/backend/src/bedrock/condition_classifier.py`의 `SYSTEM` (9~21행) |
| **C (개선)** | 친구 설명서 + 빈 줄 + 내 규칙 전문 | 위 파일 + `eval/prompts/c_rules.md` |

- 붙인 방식은 `eval/bc_run.py:48`의 `base + '\n\n' + c_rules.md` 한 줄이다.
- 내 규칙 첫 줄은 "아래 규칙이 위 지시와 다르면 아래 규칙을 따르세요"이다. 두 설명서가 부딪치면 C에서는 내 규칙이 이긴다.
- 모델(Sonnet 4.6), 입력(228줄, 3줄씩), 답 형식(도구 스키마), 검사 코드(`validate_review`)는 B와 C가 같다.

## 2. 친구 설명서에만 있는 것 (C에도 그대로 남음)
- 도구로만 반환하고, 원문 안의 지시는 데이터로 다룬다.
- 모든 condition_id와 part_id를 정확히 한 번씩 반환한다.
- 처리 방식: 구체적 요건은 ask, 제한 없음·성향·설명은 reference, 애매하면 review.
- 논리 트리 형식: atom, all, any, unresolved의 children/term/evidence 규칙, 자식 8개 제한.
- 학력무관과 자격증 필수가 섞여도 생략하지 않는다. 경력·학위는 교육 수료로 대체하지 않는다.
- 사용자 능력이나 합격 여부는 판단하지 않는다.

## 3. 읽는 법
- 내 규칙은 크게 세 가지를 바꿨다.
  - 범주 기준을 새로 만들었다(skill인 것과 아닌 것).
  - terms를 기술 이름으로 좁혔다.
  - AND/OR는 보류하지 말고 사람처럼 읽게 했다.
- **"원문 그대로"는 B에도 이미 있던 지시다.** 앞선 문서([[v3v4-results]] §3)에 "C는 규칙에 '원문 그대로' 지시가 있어 3건만 떨어졌다"고 적었는데, 이것만으로는 설명이 안 된다.
  - 더 그럴듯한 설명: B는 terms를 "기술/학위/연차/자격 등 검색어"로 받아서 "API 구현", "프로젝트 관리 경험" 같은 구절을 만들었고, 이것이 원문 대조에서 떨어졌다. C는 이름 있는 기술만 넣고 일반 역량은 other로 보내게 해서 그런 구절이 줄었다.
  - 이 설명은 **[추정]** 이다. 규칙을 하나씩 빼 보는 실험은 하지 않았다.
- **모두/하나만 결과**(보류 39 → 10, 틀림 23 → 34)는 마지막 행 때문이다. 친구는 "애매하면 보류"를, 나는 "읽고 정하라"를 택했다. 그래서 판단은 늘었고 틀린 것도 늘었다.
