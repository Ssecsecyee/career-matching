## 3. 새로 측정한 것 — 패치가 처리(treatment)를 바꾼다 **[측정, 정답 없음]**
저장된 서비스 방식 실행(B와 패치, 각 3회, 228줄)의 처리 값을 비교했다. 모델 호출은 없다.

| | 팀원 그대로 (B) | 패치 |
|---|---|---|
| 처리 분포 (3회 합 684) | 묻기 512 · 검토 89 · 참고 83 | 묻기 481 · 검토 105 · 참고 98 |
| 같은 쪽 안에서 회차끼리 처리가 같은 비율 | 97.4% | 94.7% |
| B와 패치의 처리가 같은 비율 | 87.4% | |

- B와 패치의 일치(87.4%)가 B 자체의 회차 간 일치(97.4%)보다 낮다. 그래서 패치가 처리를 바꾼다고 볼 수 있다.
- 바뀐 것의 대부분은 묻기 → 검토(44회)다.
  - 팀원 코드에서 묻기와 검토는 둘 다 질문 목록에 들어간다 **[코드 확인: `services/condition_review.py` `question_selection`]**.
  - 질문에서 빠지는 것은 참고뿐이다.
- 3회 중 2회 이상 참고로 처리된 조건: B 28개, 패치 30개, 공통 26개.
  - **패치에서 새로 질문에서 빠지는 조건 4개**: 그중 1개가 **필수(자격요건)** 조건이다. 일반 역량("…에 대한 이해") 줄이고, 내 정답 범주는 기타다. 나머지 3개는 우대 조건이다.
  - 패치에서 새로 질문에 들어가는 조건 2개: 둘 다 우대 조건이고 성향 줄이다.
- 새 공고 20건(6개씩 방식, B와 C2)에서도 처리 일치는 89.0%였다. 참고는 35 → 53회(3회 합 555)로 늘었다.
- **해석의 한계**: 어느 쪽이 맞는지는 모른다. 처리 정답이 없기 때문이다. 다만 "패치는 범주만 바꾼다"는 [[live-category-fix]] 안내서의 서술은 측정과 맞지 않는다. 전달 전에 고쳐야 한다.
- 이 결과가 요청 보고서 V3-T의 필요성을 뒷받침한다.

## 8. 사용자 판단이 필요한 것
1. **처리 정답 기준과 범위.**
   - 기준 제안: 팀원 프롬프트가 정한 정책을 따른다(구체적 요건은 묻기, 제한 없음·성향·요건 아닌 설명은 참고, 애매하면 검토). 이렇게 하면 "내 기준으로 채점" 문제가 줄어든다.
   - 범위 선택지
     - (가) 228줄 전체를 "질문해야 함 / 참고만 / 애매"로 라벨링한다.
     - (나) B와 패치가 어긋나거나 회차마다 흔들린 16줄만 판정한다. 어느 쪽 답인지는 가린다.
   - (나)는 20분이면 되고 "패치가 질문을 나쁘게 바꾸나"에는 답한다. 절대 정확도는 (가)여야 나온다.
2. **새 공고 20건을 독립 시험지로 쓸지, 라벨링 방식.**
   - 사람이 처음부터 다는 방식, 또는 GPT 초안 + 전부 검토.
   - 초안을 쓰면 앵커링 한계가 그대로 남는다.
3. **두 번째 평가자.** 팀원이나 다른 사람이 일부(예: 5건·약 50줄)를 초안 없이 라벨링할 수 있는지. 평가자 간 일치도(Cohen's Kappa)는 이것 없이는 낼 수 없다.
4. **유료 실행 승인.** §6의 항목별로 따로 승인받는다.
5. **팀원에게 요청할 것.** 운영 버전 3문항, 교육 검색·E2E용 접근(운영 화면 사용 또는 결과 추출), 두 번째 평가자.
6. **V6 판정 기준.** 관련 과정의 기준(등급 2 이상 제안), 판단 불가(U) 처리, 결과를 보기 전 확정.
7. **V-E2E 치명 오류 정의.** 제안: 필수·우대 뒤바뀜, OR을 AND로 강제, 근거 없는 교육 추천, 미확인을 미충족으로 단정.
8. **발표 숫자.** 서비스 방식 62.0%인지 화면 라벨 74.0%인지. §3 결과가 나온 뒤 처리 변화도 함께 말할지.
9. **커밋.** 지금까지의 정답·코드·문서를 커밋할지.
