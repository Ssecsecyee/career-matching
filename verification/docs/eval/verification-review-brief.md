# 검증 인수인계 — 맥락 문서에서 비어 있던 6가지와 타당성 자기점검

> **이 문서를 읽는 AI에게**
> - [[team-project-context]] 다음에 읽는다. 그 문서가 "아직 모른다"고 한 6가지를 여기서 채운다.
> - 주장마다 성격을 표시한다.
>   - **[사전]** 결과를 보기 전에 정한 지표·결과
>   - **[사후]** 결과를 본 뒤 추가한 분석
>   - **[추정]** 측정하지 않은 추론
>   - **[제안]** 아직 결정되지 않은 것
> - 검토 기준은 세 가지다.
>   1. 이 검증이 정말 서비스 신뢰성을 높이는가
>   2. 평가 방법이 그 주장을 뒷받침하는가
>   3. 심사위원의 기술 질의에 방어할 수 있는가
>
>   §6이 이 세 기준에 맞춰 약점까지 적은 자기점검이다.

## 3. 검증 설계
**원칙**: AI가 제안하고, 코드가 검증하고, 사람이 승인한다. 상세는 `docs/eval/verification-handoff.md`에 있다.

**모든 검증에 공통인 장치**
- **정답 먼저 봉인**: 정답을 확정하고 해시로 봉인한 뒤에만 실행·채점한다. 봉인 전에는 코드가 실행을 거부한다.
- **같은 조건에서 비교**
  - B = 팀원 코드·프롬프트 그대로.
  - C = 같은 코드에 내 규칙만 추가.
  - 모델(Bedrock Claude Sonnet 4.6), 데이터, 출력 형식, 팀원 검사 코드는 같다.
  - 팀원 코드는 읽기 전용으로 import해서 호출한다.
- **구간**: 공고 단위로 복원추출해 짝지은 부트스트랩(4,000회)으로 95% 구간을 낸다. 실패 횟수 비교에는 Fisher 정확 검정을 쓴다.
- **대표 지표를 미리 정함**: 대표 숫자는 결과를 보기 전에 정한다. 사후 분석은 따로 표시한다.
- **판단 기록**: 규칙이나 판단을 바꿀 때마다 `rule-log.md`에 결정자(사용자/AI)와 함께 남긴다.
- **하네스**: 보고 전에 `python harness/check.py`를 돌린다(테스트, 기록 형식, 비밀값 검사).
- **표본 크기**
  - 11/13에 macro F1 95% 구간 ±0.10을 목표로 최소 20건을 정했다.
  - 11/18에 실제 결과로 다시 쟀다. 구간은 ±0.09~0.14였다. 설계 효과는 예상(2.5배)보다 큰 6.2배였다.
  - 짝지은 비교 덕분에 차이의 구간은 1.6~2.1배 좁았다.

### 6-1. 이 검증이 정말 서비스 신뢰성을 높이는가
| 검증 | 사용자에게 닿는 경로 | 판단 |
|---|---|---|
| V1 | 공고 건수·통계가 부풀려지고, 같은 공고가 검색에 겹쳐 보인다 | **닿는다.** 다만 서비스에는 반영하지 않았다(제안 단계) |
| V3·V4 배치 | 이 경로는 운영에서 사실상 꺼져 있다. 전체 적재를 보류했고 `ENABLE_AI_CONDITION_RANKING`도 꺼짐이다 | **지금은 닿지 않는다.** 기능을 켤 때의 위험(공고 65%가 무효)을 미리 보여 준 것이다 |
| V3 실시간 | 범주는 **질문 카드의 라벨에만** 쓰인다(`services/condition_display.py`). 기술과 기타는 둘 다 "직무 조건"으로 보인다. **물을지 말지는 처리(treatment)가 정하는데, 처리는 정답에서 뺐다** | **일부만 닿는다.** 화면 라벨 정확도 55.4 → 74.0%로 기술 요구가 "경력"으로 보이는 일이 줄었다. 질문 흐름 자체가 나아졌는지는 측정하지 않았다 |
| 짧은 번호 | 번호 하나만 틀려도 그 공고의 조건 전체가 질문으로 넘어간다(`fallback_all_questions`) | 구조적으로는 막는다. 실패가 드물어(서비스 방식 0/78) **수치로 입증하지 못했다** |
| 캐시 키 | 프롬프트를 바꿔도 반영이 안 되는 실제 버그다 | **닿는다**(코드로 확인) |
| V7 | 손댈 필요가 없음을 확인했다 | 불필요한 변경을 막았다 |

### 6-2. 평가 방법이 그 주장을 뒷받침하는가
**강점**
- 정답을 먼저 봉인했다.
- 같은 모델·코드에서 프롬프트만 바꿨다.
- 짝지은 부트스트랩을 쓰고, 대표 지표를 미리 정했다.
- 사후 분석은 따로 표시했다.
- 형식 검사 결과(13 → 3)는 팀원 코드가 판정해서 내 기준이 섞이지 않는다.
- 실패한 답 원문까지 저장해 원인을 확인했다.

**약점** (심각한 순)
1. **순환성.** 정답의 범주 기준과 C 규칙이 같은 사람의 판단에서 나왔다. C의 범주 향상은 "채점 기준을 알려 주면 그 기준에 더 맞춘다"는 뜻이다. 그 기준이 서비스에 옳다는 별도 근거는 없다. 형식 검사 결과만 이 문제에서 자유롭다.
2. **처리(treatment) 미측정.** 실시간 대화를 실제로 바꾸는 것은 처리인데, 정답에서 뺐다.
3. **GPT 초안의 앵커링.** 정답의 97%(221줄)가 GPT 초안에서 출발했다. 27%를 고쳤지만, 사람이 처음부터 달았을 때와 같은지는 모른다.
4. **시험지 재사용.** v2 규칙의 형식 부분은 시험 공고의 실패를 보고 고쳤다. 범주 내용은 그대로 뒀다. 새 공고 20건으로 형식 실패와 일관성은 확인했지만, 새 공고에는 정답이 없어 정확도는 시험 공고로만 쟀다.
5. **작은 표본.** 공고 20건, 점핏 한 출처, 백엔드만 봤다. 배치(V3·V4)와 V7은 1회 실행이다.
6. **사후 지표.** 서비스 방식 재측정과 화면 라벨 기준은 결과를 본 뒤 추가했다. 대표 숫자를 바꾸면 "좋은 숫자 고르기"로 보일 수 있다.
7. **측정 코드와 운영 코드가 다를 수 있다**(§2).

### 6-3. 심사위원 질의 대비
| 예상 질문 | 답의 요지 |
|---|---|
| 정답을 직접 만들었으니 규칙을 넣은 쪽이 이기는 게 당연하지 않나? | 맞는 지적이다. 그래서 내 기준과 무관한 숫자를 앞에 둔다: 팀원 코드 자체 형식 검사 13 → 3건. 범주 숫자는 "이 기준을 쓰면"이라는 조건을 붙여 말한다 |
| 20건으로 충분한가? | 미리 계산해 정했고(±0.10), 실제 결과로 다시 쟀다(±0.09~0.14). 차이 구간이 0보다 크다. 다만 출처 하나, 직무 하나라는 한계를 같이 말한다 |
| GPT가 정답을 만든 것 아닌가? | GPT 초안을 사람이 228줄 전부 검토해 27%를 고쳤다. 고친 비율과 출처를 줄마다 기록했다 |
| 범주가 맞으면 사용자에게 뭐가 좋아지나? | 질문 카드의 라벨이 맞아진다(55 → 74%). 어떤 조건을 묻는지는 처리가 정하는데, 그건 이번에 재지 않았다고 솔직히 말한다 |
| 모델 답이 매번 다르지 않나? | 실시간은 3회 반복했다. 같은 답 비율은 86.8 → 92.1%다 |
| 팀원 서비스에 실제로 반영됐나? | 아직 아니다. 패치를 만들었고 팀원 테스트 499개가 통과한다. 반영은 팀원 결정이다 |
| 비용은? | 검증 전체 Bedrock 약 23달러다. 호출 전 계획(호출 수·토큰 추정)을 뽑고 승인을 받은 뒤 실행했다 |
| 다른 모델로도 되나? | 재지 않았다. 팀원 서비스와 같은 Sonnet 4.6만 썼다 |
