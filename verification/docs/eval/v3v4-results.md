# V3·V4 결과 — 팀원 조건 추출 프롬프트(B) vs B + 내 규칙(C)

설계는 [[verification]]에, 정답 기준은 [[labeling-guide]] V3·V4 절에 있다. 결정 기록은 [[rule-log]]의 2026-11-14~17 줄에 있다.

## 1. 무엇을 했나
- **시험 공고**: 팀원 DB(점핏) 백엔드 공고 20건. 조건 228개는 팀원 코드(`condition-split-v3`)가 자른 그대로다.
- **정답**
  - 사용자가 기준을 정했다. 무엇이 기술인가, 모두/하나만 읽는 법, 라벨링 중 나온 판단 2개가 여기에 들어간다.
  - GPT가 초안을 달았고, 사용자가 228줄을 전부 검토했다. 그중 60줄(27%)을 고쳤다. 7줄은 사용자가 처음부터 달았다.
  - 2026-11-17 11:31에 봉인했다.
- **비교**
  - 팀원 분류기를 읽기 전용으로 그대로 불렀다. Claude Sonnet 4.6(Bedrock), 조건 3개씩 묶어 B 83회, C 83회.
  - B와 C의 차이는 시스템 프롬프트에 붙는 `eval/prompts/c_rules.md`(규칙 파일 중 팀원 형식에 맞는 부분)뿐이다.
- **비용**: 약 3.9달러 (B 입력 246k·출력 74k 토큰, C 입력 324k·출력 76k 토큰).

## 3. 읽는 법
- **규칙을 붙이면 좋아진다. 두 기준 모두 95% 구간이 0보다 크다.**
- **서비스에서 차이가 큰 이유는 대부분 형식이다.**
  - B는 20건 중 13건이 팀원 코드의 검사("기술 이름은 원문 그대로여야 한다")에서 떨어졌다. 실제 서비스였으면 그 공고에서는 조건이 하나도 나가지 않는다.
  - C는 3건만 떨어졌다. (11/21 정정: "원문 그대로" 지시는 B에도 이미 있었다. 더 그럴듯한 원인은 terms 범위를 좁히고 일반 역량을 other로 보낸 규칙이지만 [추정]이다 → [[b-vs-c-prompt-diff]])
- **품질만 보면(모델 출력 그대로) +0.235다.** 형식 문제를 빼도 규칙이 기술 이름과 범주를 더 잘 맞히게 한다.
- **모두/하나만 판단**
  - C는 "모르겠다"(보류)를 39 → 10으로 줄이고 판단을 더 많이 한다.
  - 판단한 것 중 맞은 비율은 0.40 → 0.49로 오르지만, 틀린 개수도 23 → 34로 늘었다. 여기는 아직 약하다.
- **절대 점수는 아직 낮다.** C도 기술 이름 F1이 0.49~0.57로, 강의 기준(0.7)에 못 미친다.

## 3-1. 지표 점검 (11/17, 결과를 본 뒤 추가 — 사용자 질문 "왜 둘 다 낮나, 부풀린 것 아니냐")
대표 숫자는 결과를 보기 전에 정한 그대로 둔다. 다만 같은 결과를 기준만 바꿔 다시 재서 함께 적는다.

| 결과 | 기준 | B | C | C − B | 95% 구간 |
|---|---|---|---|---|---|
| 서비스 그대로 | 지금 기준 (대표 숫자) | 0.114 | 0.487 | +0.373 | 0.23 ~ 0.52 |
| 서비스 그대로 | 양쪽 다 '기술' 줄만 | 0.097 | 0.445 | +0.348 | 0.20 ~ 0.51 |
| 서비스 그대로 | 범주 무시, 이름만 | 0.131 | 0.561 | +0.430 | 0.27 ~ 0.59 |
| 모델 출력 그대로 | 지금 기준 | 0.332 | 0.567 | +0.235 | 0.15 ~ 0.33 |
| 모델 출력 그대로 | 양쪽 다 '기술' 줄만 | 0.309 | 0.541 | +0.233 | 0.14 ~ 0.35 |
| 모델 출력 그대로 | 범주 무시, 이름만 | 0.446 | 0.648 | +0.202 | 0.15 ~ 0.26 |
| 모델 출력 그대로 | 범주 무시, 이름만, 포함 일치 | **0.549** | **0.674** | **+0.125** | **0.10 ~ 0.15** |

- **"지금 기준"은 한쪽으로 기울어 있었다.**
  - 정답은 모든 줄의 기술 이름을 센다. 모델은 '기술' 범주(참고 처리 제외)로 붙인 줄의 이름만 센다. 서비스가 검색어로 쓰는 것만 세려고 이렇게 설계했다.
  - 그래서 모델이 이름을 뽑고도 그 줄을 '경력' 등으로 분류하면 놓친 것으로 세졌다. 이렇게 놓친 이름이 B 182개, C 118개(모델 출력 기준)다.
  - 양쪽을 맞춰도 점수는 크게 달라지지 않았다.
- **서비스 기준 B가 0.1대인 이유는 형식이다.** 어떤 기준으로 재도 0.10~0.17이다.
  - 20건 중 13건이 팀원 코드의 "기술 이름은 원문 그대로" 검사에서 떨어져 결과가 0이 된다.
  - 팀원 문서(`AI_CONDITION_V2_VERIFICATION_20261103.md`)도 이 검사를 공고 3건(조건 32개)으로만 확인했다. 개발 중에도 7회가 형식 검사에서 실패했다.
- **B가 검사에서 떨어진 진짜 이유 (11/17 확인)**
  - 원문에 글자 그대로 없는 이름이 B 80개(12건), C 2개(2건)였다.
  - 대부분 기술 이름이 아니라 문장을 줄인 구절이다. 예: "~ 문제 해결 경험", "API 구현", "클라우드 환경 개발 경험".
  - 대화에서 처음에 "자바 → Java처럼 이름을 바꿔서"라고 설명한 것은 확인 전 추측이었고 틀렸다.
- **팀원 서비스가 문제없이 돌아가는 이유**
  - 이 검사는 실시간 대화가 아니라 **손으로 돌리는 배치 단계**(`app/ingestion/classify_job_conditions.py`)에 있다. 한 번에 1~20건씩 돌리고, 결과는 격리 저장했다가 따로 확인한 뒤 게시한다.
  - 검사에 떨어진 공고는 `failed`로 세고 건너뛴다. 사용자에게 오류가 보이지 않는다.
  - 실시간 대화는 더 가벼운 `selected-question-v1`으로 범주·처리만 붙이고 기술 이름은 뽑지 않는다. 그래서 이 검사의 영향을 받지 않는다.
  - 팀원 코드의 모델 설정도 `global.anthropic.claude-sonnet-4-6`으로 이번 실행과 같다.
  - 운영 DB에서 실제로 몇 건이 통과·실패했는지는 읽기 권한(`job_condition_reviews`)이 없어 확인하지 못했다.
- **답의 질만 가장 너그럽게 보면 +0.125(0.10~0.15)다.** 범주를 무시하고, 이름이 서로 포함되면 맞은 것으로 쳤다. 규칙 효과는 어느 기준에서도 0보다 크지만, 크기는 기준에 따라 +0.12 ~ +0.43이다.
- **발표에서 쓸 문장**: "규칙을 붙이면 형식 검사 통과가 20건 중 7 → 17건으로 늘어 서비스에 나가는 결과가 크게 늘고(F1 0.11 → 0.49), 형식을 빼고 답의 질만 봐도 0.55 → 0.67(+0.12, 95% 0.10~0.15)로 좋아진다."

## 4. 한계 (발표에 함께 쓴다)
- **정답**: GPT 초안을 사람이 전부 검토해 27%를 고친 정답이다. 사람이 처음부터 단 정답은 아니다.
  - 정답 기준과 C 규칙이 같은 사람의 판단에서 나왔으므로, C가 유리한 것은 "규칙을 알려 주면 그 기준에 맞춘다"는 뜻이다.
  - 시험 공고를 보고 정한 판단 2개(11/16)는 C 규칙에 넣지 않았다.
- **실행 횟수**: B·C를 한 번씩만 돌렸다. 모델 답의 흔들림은 재지 않았다.
- **데이터**: 공고 20건, 점핏 한 출처, 백엔드만이다.
- **실패 처리**: 모델 답 형식 오류(B 2회, C 1회)는 서비스와 똑같이 다시 부르지 않았다.
