# 검증 설계 — 팀원 추출 프롬프트에 내 규칙을 더하면 얼마나 정확해지는가

발표 한 장에 들어갈 질문은 하나다.

> **팀원 서비스(career-matching)의 Bedrock 추출 프롬프트에 내가 만든 판정 규칙([[labeling-guide]])을 붙이면, 사람이 만든 정답과 얼마나 더 일치하는가?**

## 1. 비교 구성
| | 프롬프트 | 바뀌는 것 |
|---|---|---|
| **B** | 팀원 프롬프트 그대로 (`condition-review-v2`) | — |
| **C** | B + 내 규칙 파일 전문(`docs/eval/labeling-guide.md`) | 규칙만 |

- 모델·데이터·출력 형식·검증 코드는 B와 C가 같다. 그래서 점수 차이 = **규칙의 효과**.
- 팀원 코드는 수정하지 않고 우리 쪽에서 읽어서 호출한다.
- 정답은 AI 초안 없이 내가 직접 라벨링한다(블라인드). 라벨링 화면은 원문만 보여 준다.
- 규칙은 연습용 22건(Techmap)으로만 다듬고, 시험 공고(팀원 DB의 점핏)는 봉인 후 **한 번만** 채점한다. 시험 공고와 연습 공고는 출처·형식이 달라 규칙이 처음 보는 형식에서도 통하는지 본다.

## 2. 시험 공고는 몇 건이어야 하나 — **최소 20건**

### 2-1. 공식
비율(정밀도·재현율)의 95% 신뢰구간 반폭을 ±d 이하로 만들려면

$$n = \frac{z^2\,p(1-p)}{d^2} \;\le\; \left(\frac{z}{2d}\right)^2 \quad (z=1.96,\ \text{최악 } p=0.5)$$

| 오차 ±d | 필요한 n (공고×기술 쌍) |
|---|---|
| ±0.15 | 43 |
| ±0.10 | 97 |
| ±0.07 | 196 |
| ±0.05 | 385 |

연습 22건에서 공고 하나에 필수·우대 정답 쌍이 평균 **12.1개**이므로, 공식만 보면 ±0.10에 **약 8건**이면 된다.

### 2-2. 공식이 틀리는 지점: 같은 공고 안의 기술은 독립이 아니다
공식은 쌍 하나하나가 독립이라고 가정한다. 실제로는 한 공고의 기술들이 **함께** 맞거나 틀린다(예: 섹션이 잘못 나뉜 공고는 그 안의 기술이 한꺼번에 틀린다). 이런 군집 표본에서는 같은 정확도를 얻는 데 표본이 더 필요하다(설계 효과, design effect).

### 2-3. 데이터로 확인: 공고 단위 부트스트랩
연습 22건(사람 승인 정답)과 그 공고들에 대한 Bedrock 추출 결과로, **공고를 통째로** 복원 추출해 F1을 4,000번 계산하고 95% 구간 폭을 쟀다. 재현: `python -m eval.sample_size` (seed 7).

| 시험 공고 수 | F1 95% 구간 |
|---|---|
| 10 | ±0.147 |
| 15 | ±0.120 |
| **20** | **±0.102** |
| 30 | ±0.083 |
| 40 | ±0.074 |
| 60 | ±0.059 |

공식은 ±0.10에 약 8건, 실제 데이터는 **20건** → 설계 효과 약 **2.5배**.

### 2-4. 결정
- **최소 20건**(F1 ±0.10). 시간이 되면 30건(±0.08).
- 10건(±0.15)으로는 B와 C의 차이가 15%p보다 작을 때 효과를 말할 수 없다.
- B와 C는 **같은 공고**로 비교하므로 두 점수의 **차이**에 대한 구간은 위 표보다 좁다. 발표에는 차이와 그 구간을 함께 쓴다: "C − B = +x%p (95% 구간 a ~ b)".
- 한계: 설계 효과를 연습 데이터(Techmap 22건, 다른 출처)로 추정했다. 시험 데이터로 다시 재서 함께 보고한다.

### 2-5. 시험 결과로 다시 잼 (2026-11-18, 모델 호출 없음)
봉인 정답으로 채점한 B·C 결과(20건, 정답 기술 쌍 336개)에서 공고를 통째로 4,000번 복원 추출했다. 재현: `python -m eval.sample_size_check` (seed 20261118).

| 확인 | 계획 (11/13) | 실제 | 판정 |
|---|---|---|---|
| 한 버전 macro F1의 95% 구간 | ±0.10 | 모델 출력 B ±0.11 · C ±0.11, 서비스 B ±0.09 · C ±0.14 | 거의 계획대로 |
| 설계 효과 (micro F1, 쌍 독립 공식 대비) | 2.5배 | 모델 출력 **6.2배**, 서비스 20.6배 | **예상보다 큼** |
| 차이 C − B의 95% 구간 (같은 공고로 짝지음 vs 따로 뽑음) | "더 좁다" | 모델 출력 macro 폭 0.19 vs 0.30 (**1.6배**), micro 0.17 vs 0.35 (**2.1배**) | 짝지음 효과 확인 |
| 20건으로 80% 확률로 잡는 최소 차이 (공고별 F1) | — | 모델 출력 0.13, 서비스 0.22 | 관측 차이 0.24 · 0.37이 넘음 |

- **설계 효과가 연습 추정보다 컸다.** 공식(쌍 독립)만 믿었으면 구간을 2~4배 좁게 잘못 보고했을 것이다. 서비스 기준이 20배인 이유는 형식 검사에 떨어진 공고가 기술 전부를 한꺼번에 0으로 만들기 때문이다.
- **그래도 20건은 충분했다.** 계획 ±0.10에 가까운 폭이 나왔고, 짝지은 비교 덕분에 차이의 구간은 한쪽 점수 구간보다 좁다. 관측된 차이(0.24, 0.37)는 20건으로 잡을 수 있는 최소 차이(0.13, 0.22)보다 크다.
- **20건으로 못 잡는 크기도 미리 알 수 있다.** V3 실시간의 공고별 평균 차이 +0.061은 같은 계산의 최소 검출 차이 0.115보다 작다. 그래서 그 구간이 0을 포함한 것은 예상 범위 안이다 ([[v3-live-results]]).
- 95%(z = 1.96)는 "우연인데 효과가 있다고 말할 확률"을 5%로 묶는 관례, 80%(z = 0.84)는 실제 효과를 놓칠 확률을 20%로 묶는 관례를 따랐다. 둘 다 11/13 결과를 보기 전에 정했다.

## 3. 채점
- 단위: (공고, 기술 term, 필수/우대). 필수/우대는 팀원 로직처럼 **칸**(자격요건/우대사항)으로 정해진다.
- **본 숫자: macro F1**(공고별 F1의 평균) — 강의 기준(F1 ≥ 0.7)과 같은 방식이고, 사용자가 공고를 하나씩 보는 경험에 가깝다.
- **보조 숫자: micro F1**(모든 쌍을 모아 한 번 계산) — 기술이 많은 공고에서도 잘 되는지.
- 호출 수: 팀원 코드는 조건을 3개씩 묶어 부르므로 20건(조건 228개)에 **B 83회 + C 83회 = 166회**다(`python -m eval.bc_run plan`, 11/16). 처음에 적은 "40회"는 공고당 1회로 잘못 셌다.
- 실행 `python -m eval.bc_run run --variant B --live` → 채점 `python -m eval.bc_score`. 봉인 전에는 실행·채점 모두 거부한다.
- 연습 22건 참고치(규칙을 넣은 Bedrock, 업무→필수 반영): micro 0.793 · macro 0.758. 연습용·정답 초안을 같은 계열 모델이 써서 유리하게 기울 수 있어 성능 근거로 쓰지 않는다.
- 그 밖에 보고: 근거 문장 위조 수(원문에 없는 인용), 범주별(기술·자격증 등) 정확도.

## 4. 팀원 추출 로직 (2026-11-13 코드 읽음, 수정 없음)
`career-matching` `condition-review-v2` (`app/backend/src/schemas/condition_review.py`, `services/condition_review.py`, `bedrock/condition_classifier.py`):
- 읽는 칸: **자격요건 → required, 우대사항 → preferred** 두 칸만. 수준은 칸 위치로 코드가 정한다. **주요업무·기술 태그·제목은 읽지 않는다.**
- 조건 줄마다 모델이 정함: category(skill / experience / education / **certificate** / attitude / other), treatment(ask / reference / review), logic(atom / all / any / unresolved — 명시적 "또는/혹은"만 any), parts.terms(원문 그대로, 번역·동의어 정규화 금지).
- 서비스가 쓰는 것: category=skill이고 reference가 아닌 조건의 terms → 검색 순위 힌트. 자격증·경력·학력은 사용자에게 묻는 조건.
- 내 규칙과 다른 점: 규칙 1(태그=필수)·5(제목=필수)·11(주요업무=필수)·이름 표준화는 팀원 로직 범위 밖.
- **정정 (같은 날 추가 조사)**: 위 `condition-review-v2`는 **오프라인 배치**(`app/ingestion/classify_job_conditions.py`, 격리 → 확인 → 게시) 경로다. **실시간 서비스**는 공고를 고를 때 더 가벼운 `selected-question-v1`(`bedrock/question_reviewer.py`)로 조건 줄마다 **범주·처리만** 붙이고 검색어는 뽑지 않는다. 그래서 검증은 두 층: (a) 범주·처리 정확도 — 두 경로 공통, (b) 기술 검색어 F1 — 오프라인 경로. 흐름 그림과 위치는 [[verification-handoff]].
