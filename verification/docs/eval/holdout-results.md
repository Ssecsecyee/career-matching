# V3-H — 처음 보는 공고에서도 규칙 v2가 통하나 (새 공고 20건·185줄)

## 1. 무엇을 확인했나
- 규칙 v2는 첫 시험 공고(20건·228줄)를 보며 만들었다. 이 공고에만 맞춘 규칙일 수 있다.
- 그래서 규칙을 만들 때 한 번도 보지 않은 공고로 다시 쟀다.
  - 새 공고 20건(185줄): 시험 공고와 회사가 겹치지 않고, 대화에서 본 공고도 뺐다(`eval.live_run.fresh_jobs`, seed 20261118).
  - 친구 그대로(B)와 규칙 v2(C2)의 답은 11/18에 3회씩 미리 저장해 뒀다. 정답을 만들기 전이다.
  - 방식: 6개씩 보내는 방식(bounded)으로 먼저 무료 채점했다(§3).
  - 그 뒤 사용자 승인으로 **서비스 방식에서 친구 그대로 대 최종 패치(C2G)**를 새로 돌렸다(§3-3).

## 2. 정답을 어떻게 만들었나
- 첫 시험지와 같은 방식이다. ChatGPT 초안(모델명 미기록)을 사용자가 화면에서 185줄 전부 검토했다.
  - 사용자가 바꾼 줄: **85/185 (46%)**. 첫 시험지는 60/221(27%)였다.
  - 범주를 바꾼 54줄 중 42줄이 기술→기타다. 기술 이름 칸을 바꾼 줄 71, 관계를 바꾼 줄 45.
- 지침과 다른 점: 사용자는 "기술"을 지침보다 좁게 잡았다.
  - 업무 도메인(금융·커머스 등), 어학(영어), REST API, AI 도구, 일부 도구 이름을 기타로 두고, 그 줄의 기술 이름 칸을 비웠다.
  - 지침과 라벨링 화면은 "도메인·어학도 기술"이라고 적혀 있다.
  - 첫 시험지에서도 뒤쪽 공고에서 같은 방향의 흔들림이 있었다(도메인·REST·어학 7줄을 기타로).
- 이 차이를 보고 **점수를 보기 전에** 기준을 정했다([[rule-log]] 11/19 "V3-H 라벨 기준·주지표").
  - 라벨은 그대로 봉인한다(사용자 결정).
  - 주지표는 **사용자 화면에 보이는 라벨**로 채점한 결과다.
    - 친구 서비스는 범주를 질문 카드 라벨로만 쓴다(`services/condition_display.py`). 기술과 기타는 둘 다 "직무 조건"으로 보인다.
    - 그래서 기술/기타를 어떻게 나누든 이 점수는 거의 바뀌지 않는다.
  - 범주를 그대로 맞추는 점수는 보조로만 쓰고, "좁은 기술 기준"이라고 적는다.
  - 판정 규칙(AI 제안, 점수 보기 전에 적음. 사용자가 점수를 본 뒤 11/19에 그대로 승인):
    - 공고별 차이의 95% 구간 하한이 0보다 크면 → 재현
    - 차이는 0보다 크지만 구간이 0을 포함하면 → 방향은 같으나 확정 못 함
    - 차이가 0 이하면 → 재현 안 됨

### 3-3. 서비스 방식, 최종 패치 (11/19, 호출 120회)
- 무엇을: 친구 서비스와 같은 방식(공고 통째로 한 번, 잘리면 6개씩 대체, 그 밖의 실패는 공고 전체를 질문으로)으로 친구 그대로(B)와 **넘길 패치 그대로(C2G: 규칙 v2 + 짧은 번호 + 캐시 키 v2 + 안전장치)**를 회차마다 번갈아 3회씩 돌렸다.
- 주지표·판정 규칙은 실행 전에 기록했다([[rule-log]] 11/19 "V3-H 서비스 방식 실행"). 정답은 §2의 봉인본 그대로다.
- 모델 Claude Sonnet 4.6(서울 리전), 친구 클라이언트 설정(15초, 재시도 없음). 실패한 공고는 다시 부르지 않았다.

| 기준 | 친구 그대로(B) | 최종 패치(C2G) | 공고별 차이 (95% 구간) |
|---|---|---|---|
| **화면 라벨 (주지표)** | **55.3%** | **78.0%** | **+19.7%p (+10.7 ~ +30.4)** |
| 범주 그대로 (보조) | 41.6% | 61.8% | +16.9%p (+10.3 ~ +24.2) |

- 판정: 구간 하한 +10.7%p > 0 → **서비스 방식·최종 패치로도 재현됐다.**
- 시험 공고의 서비스 방식(55.4 → 74.0%, +16.4%p)과 비교해도 효과가 줄지 않았다.

|---|---|---|
| 공고 전체가 질문으로 넘어감 (형식 실패) | 1 (14줄) | 0 |

| 응답 시간 중앙값 / 95번째 / 최대 | 6.7 / 9.1 / 9.4초 | 5.6 / 8.0 / 8.6초 |

- **친구 그대로의 실패 1건은 번호 베끼기 오류였다.** 진단(호출 없음): 모델이 64자 번호 1개를 틀리게 베꼈고, 번호만 고치면 친구 검사를 통과한다. 짧은 번호 패치가 막으려는 바로 그 오류다. 다만 60번 중 1번 대 0번이라 통계적으로 말할 수는 없다.
  - 이 공고는 실제 서비스라면 14줄 전부를 질문으로 묻게 된다. 그래서 "3회 모두 같은 라벨" 비율에도 반영됐다.
- 비용: 입력 약 27.7만, 출력 약 12.5만 토큰. Sonnet 단가(입력 3달러, 출력 15달러 / 100만 토큰)로 약 2.7달러다 [추정]. 실패한 호출 1건의 토큰은 빠져 있다.
- 남은 가장 큰 오류는 여전히 "~경험" 직무 조건을 경력으로 부르는 것이다(첫 회차 34줄, B는 67줄). 경력 정밀도 0.19 → 0.33.

**처리(물을지) 변화 — 정답 없음, 바뀐 줄만 확인** (`python -m eval.treatment shift --set fresh`)
- 두 쪽의 처리가 같은 비율 91.3%. 회차 간 같은 비율은 B 98.5%, C2G 95.7%다.
- 대체로 묻지 않는 줄: 12 → 14. 새로 빠진 3줄, 새로 들어간 1줄. 줄 원문을 확인했다.
  - 빠진 필수 2줄은 둘 다 "원활한 커뮤니케이션" 줄이다. 사용자 정책(11/19, "그런 건 굳이 묻지 말자")과 맞다.
  - 빠진 우대 1줄은 "GIS / Spatial 분야" 소제목이다. 정답에서도 "조건 아님"이다.
  - **새로 들어간 필수 1줄은 "[핵심 기술 역량]" 소제목이다.** 안전장치가 "필수 칸인데 요건 아님"을 질문으로 되돌린 경우다. 불필요한 질문 1개가 생긴 셈이다. 필수를 빠뜨리지 않으려고 고른 쪽의 비용이다.
- 이 4줄은 결과를 본 뒤 원문을 읽고 해석한 것이다(사후). 처리 정답이 따로 있는 것은 아니다.

## 4. 결과가 라벨 기준에 흔들리나 (사후 민감도, 결과를 본 뒤 추가)
- 화면 라벨 기준으로는 사용자 검토가 바꾼 줄이 11/185뿐이다(경력↔직무 조건 7, 성향·자격 4).
- 사용자 검토를 무시하고 ChatGPT 초안을 그대로 정답으로 써도 결과가 같았다.
  - 화면 라벨: B 54.6% → C2 77.5%, 공고별 +19.6%p (+11.1 ~ +29.1)
  - 범주 그대로(초안은 지침의 넓은 기술 기준에 가깝다): 50.1 → 71.2%, +17.8%p (+10.2 ~ +25.9)
- 따라서 이번 차이는 "기술을 넓게 보든 좁게 보든", "검토를 하든 안 하든" 유지된다.

## 5. 한계
- **운영 코드가 아니다.** 서비스 방식(§3-3)도 GitHub main의 친구 코드를 독립 환경에서 부른 것이다. 운영과 같은지는 [[production-baseline]]이 다룬다.
- 반복은 3회뿐이다. 정답률이 규칙 몫인지 짧은 번호 몫인지는 나눠 재지 않았다.
- **처리(물을지 말지)는 재지 않았다.** 이 정답에는 범주만 있다. 처리 문제는 [[treatment-results]]에서 따로 다뤘다.
- **정답은 한 사람이 GPT 초안을 검토해 만들었다.** 초안에 끌려가는 효과(앵커링)는 남는다.
  - 팀원 두 번째 평가(이 중 5건·52줄, 초안 없이)가 오면 일치도로 일부 확인한다.
  - 팀원 안내문은 넓은 기술 기준이다. 그래서 일치도는 범주 그대로와 화면 라벨 두 기준으로 낸다(`python -m eval.second_rater score`의 `display_basis`).
- **기술 이름 칸은 이번 채점에 쓰지 않았다.** 사용자가 좁은 기준으로 비운 줄이 있다. 이 정답지로 기술 이름(V4)을 채점하려면 그 전에 기준을 다시 정해야 한다.
- 백엔드 공고만 봤다. 다른 직무는 재지 않았다.
