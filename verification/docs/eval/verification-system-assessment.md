# EDU-CARE 검증 시스템 종합 평가 보고서

## 0. 요약
- **무엇을 했나**: 팀원의 챗봇 서비스(EDU-CARE, `career-matching`)를 한 줄도 고치지 않고 읽기 전용으로 불렀다. 워크플로에서 검증이 필요한 곳 7군데를 같은 모델·같은 데이터로 "친구 그대로(B) 대 규칙·패치"로 쟀다. 운영 공개 체험 화면에서도 교육 추천과 전체 여정을 직접 확인했다.
- **검증 시스템이 실제로 잡아낸 것**: 형식 실패의 진짜 원인(긴 번호 베끼기), 프롬프트를 바꿔도 반영되지 않는 캐시 키 버그, **우리 패치가 필수 조건을 빼먹는 회귀**, 운영 화면의 검색 누락(한·영 표기, 지역 조건)과 OR을 AND로 읽는 치명 오류, 공고 재게시 22.4%, 그리고 우리 자신의 과장된 결론 3건.
- **가장 강한 결과**: 처음 보는 공고 20건에서 서비스 방식·최종 패치로 조건 라벨 정답률 55.3% → 78.0%(공고별 +19.7%p, 95% +10.7~+30.4). 지표와 판정 규칙은 점수를 보기 전에 정했다.
- **가장 큰 약점**: 정답이 사실상 한 사람 기준이다(두 번째 평가 안 함). 운영이 어느 코드인지 확인하지 못했다. 서비스에 반영된 것은 0건이다.
- **종합**: 검증의 설계·재현성·투명성은 강하다. 반면 정답의 독립성과 운영 적용은 약하다. 그래서 이 결과는 "GitHub 코드 기준, 한 사람 정답 기준으로 측정한 개선과 발견"이다.

## 4. 검증 시스템이 잡아낸 것 — 효과 평가
"검증을 했더니 무엇이 달라졌나"를 기준으로 본다.

| 발견 | 어떻게 잡았나 | 결과 |
|---|---|---|
| 친구 배치 추출이 친구 자체 형식 검사에서 13/20 무효 | 같은 검사 코드로 B·C 비교 | 규칙 파일로 3/20 (내 기준과 무관한 숫자) |
| 형식 실패의 원인은 규칙이 아니라 **64자 번호를 1~3글자 틀리게 베낀 것** | 버려진 답 원문 저장 → 번호만 고쳐 친구 검사 재실행 | 짧은 번호 패치. 새 공고 서비스 방식에서 1 → 0 |
| **캐시 키가 v1로 고정**돼 프롬프트를 바꿔도 예전 답이 나감 | 코드 읽기 | 패치에서 v2로 올림 |
| 측정 방식(6개씩)과 서비스 방식(공고 통째)이 다름 | 코드 읽기 | 서비스 방식으로 다시 잼 |
| **우리 패치가 필수 조건을 질문에서 뺌**(8/48) | 처리 변화 측정 → 가린 16줄 사람 판정 | 코드 안전장치. 배포 전에 잡은 회귀 |
| 운영 교육 검색이 한·영 표기·지역 조건 때문에 놓침 | 질의 20개 + AI 없는 목록 검색으로 DB 확인 | 놓친 원인(표기·지역·OR 되물음·조건 무시)을 팀원 메시지 초안에 정리 |
| 운영 E2E에서 OR을 AND로 해석, 경력 조건을 말없이 버림, "~"가 취소선 | 시나리오 10개 | 치명 1건 기록 |
| 공고 22.4%가 재게시 사본 | 두 번의 블라인드 사람 확인 | 수요 순위는 거의 그대로임도 확인 |
| 라벨 기준이 지침보다 좁아짐 | 봉인 전 검토 결과 점검 | 점수 보기 전에 화면 라벨을 주지표로 정함 |
| **우리 문서의 과장 3건** | 측정·외부 검토와 대조 | "category만 바꾼다" 정정, V7 "규칙 필요 없다" → "효과 확인 못 함", "벡터 검색 구축 안 함"이 낡은 정보임을 기록 |

→ 검증 시스템은 **남의 버그와 우리 자신의 실수를 모두 잡았다.** 특히 "우리 패치가 사용자에게 해를 줄 수 있다"를 배포 전에 찾은 것이 이 시스템의 존재 이유를 가장 잘 보여 준다.

## 5. 평가 방법의 타당성
**강점**
- 사전 기록: 새 공고에서는 주지표·판정 규칙을 점수 전에 적었다. 판정 규칙은 사용자가 승인했다(점수를 본 뒤였다는 것도 기록).
- 재현: 효과가 시험 공고(+16.4%p)보다 새 공고(+19.7%p)에서 줄지 않았다. 6개씩·서비스 방식 두 방식 모두에서 재현됐다.
- 민감도: 사람 검토 대신 GPT 초안을 정답으로 써도 같은 차이(+19.6%p)였다.
- 나쁜 결과 보존: V7 효과 없음, 관계 오답 증가, 패치 회귀, E2E 실패를 그대로 적었다.
- 재현 가능: 저장 실행 8항목을 호출 없이 다시 채점할 수 있고, 하네스가 매번 확인한다.

**약점**
| 약점 | 영향 | 상태 |
|---|---|---|
| 정답이 한 사람 기준(GPT 초안 + 사용자 검토 27%·46% 수정) | 범주 개선이 "내 기준에 맞춰짐"일 가능성 | 두 번째 평가 **안 함**. 새 공고 재현과 GPT 초안 민감도로 일부 완화 |
| 두 정답지의 "기술" 기준이 다름 | 범주 그대로 점수를 두 시험지끼리 비교 불가 | 기록만 함. 지침 결정 **안 함** |
| 처리 정답이 16줄뿐, 안전장치를 만든 그 줄로 효과 확인 | 처리 품질의 절대 수준은 모름 | 228줄 처리 정답 **안 함** |
| 운영 코드 미확인 | "운영 서비스가 좋아진다"고 말할 수 없음 | **안 함** |
| 표본: 20+20건, 점핏 한 출처, 백엔드만, 반복 3회 | 다른 직무·출처로 일반화 불가 | 그대로 |
| 일부 사후 분석(시험 공고 화면 라벨, V6 0건 처리, 처리 정책 변경) | 결과를 본 뒤 고른 기준 | 모두 [사후] 표시 |
| V6·E2E 파일럿(1회, 순위 가리지 않음, Hit@3만) | 추천 품질 지표가 거칠다 | 그대로 |

## 10. 발표에서 말할 수 있는 것 / 말하면 안 되는 것
**말할 수 있다**
- "처음 보는 공고에서도 조건 라벨 정답률이 55% → 78%로 올랐다. 지표는 점수 전에 정했다."
- "친구 코드 자체 형식 검사에서 무효가 13/20 → 3/20으로 줄었다." (내 기준과 무관)
- "우리 패치가 필수 조건을 빼먹는 부작용을 배포 전에 검증으로 잡았고, 코드 안전장치로 막았다."
- "형식 실패의 원인은 모델이 긴 번호를 베끼다 틀리는 것이었고, 짧은 번호로 바꿨다."
- "운영 화면의 교육 추천은 보여 준 것은 정확(32/32)하지만, 표기 차이로 20개 중 9개를 놓친다."
- "효과가 없던 것(상담 답변 규칙)과 나빠진 것(관계 오답)도 그대로 보고한다."

**말하면 안 된다**
- "운영 서비스가 좋아졌다" — 반영 0건, 운영 코드 미확인
- "정답이 객관적이다" — 한 사람 기준, 일치도 미측정
- "상담 규칙은 필요 없다" — 효과를 못 찾았을 뿐 같다는 증거가 아님
- "AND·OR 처리를 개선했다" — 오답이 늘었다
- "교육 추천 정확도 55%" 같은 단일 숫자 — Hit@3 파일럿이고 정밀도와 놓침을 함께 말해야 한다
